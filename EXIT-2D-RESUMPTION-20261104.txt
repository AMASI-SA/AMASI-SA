4. تصميم الخدمات المستهدفة — أربع خدمات دائمة ووظيفة ترحيل منفصلة
أ) Web/API: الموقع وواجهات الموظفين وAuth والجلسات وRBAC، استقبال webhook مع التحقق من التوقيع، وقراءات سريعة. يستقبل الأعمال الدائمة ويثبتها في inbox قبل الإقرار، ثم يعيد نتيجة/معرف مهمة حسب العقد الحالي. لا schedulers عامة ولا إرسال فواتير خلفي. العمليات التفاعلية الحالية ذات الأثر الخارجي تحتاج جردًا قبل نقلها؛ لا تغيير عقودها ضمن هذه المراجعة.
ب) Worker الإعلانات والمزامنات: Snapchat/Meta/Google/TikTok، CAPI، مزامنة سلة وtokens والمنتجات والطلبات، review resume والتسليم وshipping/payment inbox والـoperational push وفق جرد ملكية دقيق. المهام التشغيلية الإضافية هنا معلنة بدل ضياعها خارج التقسيم الرباعي. أي فصل خامس لاحق قرار مستقل.
ج) Worker التقارير ولوحة التحكم: exports وPDF الثقيلة والتجميعات وread-model snapshots. Web يقرأ آخر snapshot مع وقت تحديثه؛ تُعاد استخدام معادلات الربحية والمحاسبة الحالية دون إعادة اشتقاقها. حدود CPU/RAM وطوابير مستقلة تمنع تقريرًا ثقيلًا من تعطيل الموظفين.
د) Worker المحاسبة وقيود: يشغّل wrappers للعمل الحالي فقط ويحافظ على legacy_pipeline_frozen وPlan-B والأهلية والدفعات وموانع التكرار كما هي. operational_balance يُصنف هنا مبدئيًا بعد مراجعة آثاره. إيقاف عام مستقل للإرسال، concurrency أولية واحدة، ومراقبة reconciliation.
هـ) Migration job: مرحلة واحدة مضبوطة لكل source/schema version؛ لا backfill أو cleanup مالي تلقائي. تُراجع كل index جديدة وTTL/unique على نسخة معزولة أولًا. Web readiness ترفض مخططًا غير مكتمل.
تُستخدم صورة تطبيق موحدة immutable مع command مختلف لكل دور. لكل خدمة هوية وصلاحيات وأسرار وحدود موارد؛ لا حاجة لإعادة كتابة التطبيق إلى microservices أو اعتماد Redis لمجرد الفصل.
تُبنى طبقة تنفيذ فوق inbox/leases الموجودة في Mongo حيث تحقق العقود. لا يُنشأ queue جديد قبل تقييم الموجود. Web والمزامنة لا يمتلكان أسرار إرسال قيود إلا إذا أثبت جرد endpoint تفاعلي ضرورة انتقال تدريجي محدد ومراجع.
قفل سبتمبر singleton واحد يصلح كمرحلة انتقال لعامل واحد، ولا يكفي لثلاثة عوامل. التصميم الجديد يحتاج role-scoped leases مع tenant/job keys، وجسر ملكية يمنع legacy worker والـroles الجديدة من العمل معًا أثناء النقل. أسماء leases الجديدة وحدها لا توقف القديم.
لا ادعاء exactly-once بين Mongo ومزود خارجي: تثبيت job identity وunique dedupe وCAS/fence وheartbeat، ثم provider idempotency إن دعمه المزود. نجاح خارجي مع timeout داخلي يصبح outcome_unknown ويخضع للاستعلام والمصالحة، لا blind resend. لا تغيير لخوارزمية إرسال الفواتير الآن؛ أي دعم ناقص يُرفع كمانع قبول مستقل.

6. خطة MongoDB والملفات والأسرار — تصميم فقط
قبل أي اتصال/تصدير: إثبات production deployment -> DB/cluster identity، الإصدار وFCV وreplica/sharded topology، مالك الحساب وصلاحية export/restore، أحجام collections/indexes/TTL، backup ID وزمنه وretention ونافذة الاستعادة. لا نفترض ملكية Atlas ولا نستخدم اتصالًا تاريخيًا مكشوفًا. أدلة سبتمبر القديمة لا تثبت أن هذه المعلومات ما زالت ناقصة عند المالك اليوم؛ هي غير متحققة في هذه الجولة.
الأفضل فصل نقل compute عن نقل DB إذا سمحت الملكية والشبكة: استخدام نفس DB أولًا بعد اعتماد الوصول وملكية الكتابة، ثم ترحيل DB في نافذة أخرى. لا تفعيل وصول جديد الآن.
إذا لزم نقل DB معًا: backup متسق ثم restore تجريبية واختبارات مطابقة؛ في replica set يمكن mongodump --oplog مع mongorestore --oplogReplay إذا الصلاحيات والتوبولوجيا تسمح. --oplog ليس مع --db/--collection وليس حلًا لـmongos/sharded. يُستخدم snapshot/live migration مدعوم أو توقف كتابة منضبط عند تعذر CDC؛ لا وصفة dump عامة تضمن عدم الفقد.
الدلتا التي تحدث بعد نهاية dump لا تغطيها --oplog تلقائيًا؛ تلزم CDC مدعومة مستمرة حتى حاجز التحويل أو تجميد كل الكتابات وأخذ نسخة نهائية متسقة. احتفظ بمعرفات الطلبات والفواتير والدفعات وinbox/outbox والـdedupe وcheckpoints وحالات outcome_unknown؛ لا تصفرها ولا تعِد enqueue تلقائيًا.
التحقق: counts وcanonical hashes حسب tenant/window، indexes/options وTTL/unique، references، أرصدة ونتائج تقارير مقارنة دون كتابة مالية، عينات تاريخية وحديثة، dead letters/checkpoints والتشفير والمرفقات. restore لا تُقبل بمجرد ping.
الملفات: جرد Mongo Binary/GridFS إن وجدت، paths/volumes/buckets والـPDF الأصلية وصور المنتجات والمرفقات. مثال مؤكد في الإنتاج: product_media_upload_routes.py يحفظ Binary(content) وsha256 في mezan_product_media_uploads_v2 مع TTL سبعة أيام؛ لذلك نسخ directory وحده لا ينقل جميع الملفات. ليست كل PDF محفوظة كأصل؛ regeneration لا تضمن byte identity.
تُحفظ الملفات الموجودة في Mongo ضمن نقل DB أولًا بلا إعادة تصميم متزامنة. الملفات الخارجية: manifest بالمعرف والحجم وSHA256 وMIME والمالك/tenant، نسخ مبدئي ثم delta نهائية عند حاجز الكتابة، فحص جميع hashes وإعادة الفتح من الخدمتين بعد restart. Object Storage خاص وversioned مع روابط قصيرة العمر وتحقق RBAC؛ local disk مؤقت فقط. لا حذف للأصل قبل انتهاء فترة الرجوع المعتمدة.
الأسرار: جرد أسماء وإصدارات فقط، نقل من المالك عبر secret manager خارج Git والصورة والlogs. مفاتيح SALLA/QOYOD/META/GOOGLE/SNAPCHAT/TIKTOK الحالية والسابقة وMEZAN_CUSTOMER_PII_ENC_KEY وأسرار sessions/JWT وOAuth/webhooks تُحفظ بما يضمن فك البيانات والجلسات. لا توليد بديل عشوائي لمفتاح تشفير قائم، ولا rotation متزامنة مع النقل. اختبار decrypt على بيانات مصرح بها في بيئة معزولة لاحقًا؛ المفاتيح الاصطناعية لا تستخدم للإنتاج.
لا رفع بيانات عملاء أو أسرار إلى Actions artifacts. حقوق download/restore والجدار الشبكي وفصل حسابات الاختبار شرط قبل تجربة نسخة حقيقية لاحقًا.

7. خطة الاختبار المعزولة وإعادة الاستخدام
مرحلة A: الاحتفاظ بأرشيف سبتمبر وتسجيل provenance/hashes. نقل انتقائي للـharness والاختبارات إلى نسخة حديثة دون backport ملفات الأعمال. جرد callbacks/tasks والمنافذ وsubprocesses وimport-time writes وAuth/readiness. إعادة استخدام independent runtime كتصميم مع تكييفه للواجهات الحالية؛ لا اعتباره ملفًا جاهزًا للتشغيل.
مرحلة B: Linux Docker موجود ومعتمد لاحقًا، synthetic Mongo مستقلة لكل سيناريو، network=none مع loopback، ملفات readonly/tmpfs، بلا credentials ولا ports ولا provider/SMTP حقيقي. لا تثبيت Docker/WSL تلقائيًا. فحص guard قبل أول application import وإثبات عدم وجود outbound.
مرحلة C: إعادة EXIT-2C متعددة العمليات على المصدر الجديد، ثم EXIT-2D deny/unavailable/success والدورة الكاملة: review/draft/finalize/allocation/supplier/receipt/assembly/PDF والصور وwebhook/restart. حل فجوة R1/R2 بانتقال قانوني مدعوم أو إعلان عدم انطباق المتطلب صراحة؛ لا تزوير نجاحه.
مرحلة D: إثبات Web بلا schedulers/migration lifecycle writes، وكل عامل لا يبدأ مهمة عامل آخر. اختبار تسليم ownership بين نسختين/بين legacy والـroles، duplicate job وfence loss وrestart بعد provider success وقبل DB ack، clock skew وretry وdead-letter، SIGTERM ثم kill لمهمة تقاوم الإلغاء. startup claims وحدها لا توقف side effect سبق إطلاقه.
مرحلة E: قياس API p95/p99 وRSS/CPU/event-loop lag وMongo connection pools وqueue age/report freshness تحت تزامن واقعي. أربع خدمات بمجموع replicas غير محدود قد تضاعف pools؛ لا توسع web عشوائيًا. تُحدد حدود قبول الأداء من خط أساس مقاس واتفاق العمل، لا أرقام اعتباطية.
مرحلة F: backup/restore كاملة مع ملفات وأسرار مأذون بها لاحقًا في بيئة منفصلة ومنع outbound افتراضيًا، وتجربة cutover/rollback بمؤشرات تكرار/فقد صفر على fixtures، ثم مراجعة artifact/Intent النهائي. CI الجديد يحتاج تقدير jobs/ميزانية جديدة؛ حصة سبتمبر 38/40 ليست تصريحًا متجددًا ولا رصيدًا صالحًا اليوم.

8. خطة الانتقال التدريجي المستقبلية للإنتاج — تحتاج اعتمادًا مستقلًا
0) تثبيت source SHA وبناء image digest مع مراجعة security/role matrix وrestore drill وDNS/OAuth/cookies/RP ID/CORS/webhook inventory. الحفاظ على النطاق العام يقلل تغيير عقود sessions/passkeys؛ Preview ليس إثباتًا لنطاق الإنتاج.
1) نشر بيئة جديدة معزولة بعد الموافقة والتكلفة، shadow reads/fixtures فقط، والعمال الخارجيون غير مسلحين. لا replay لـPOST مالية أو إعلانية عبر shadow traffic.
2) إذا استُخدمت DB مشتركة، canary Web يبدأ بقراءات مصنفة آمنة فقط والعمليات غير القابلة للعكس تبقى في writer واحد. لا canary نسبي على قاعدتي بيانات مستقلتين قابلة للكتابة.
3) نقل worker التقارير أولًا بعد إثبات عدم ازدواج جدولة التجميعات؛ ثم المزامنات أسرةً واحدةً مع drain/checkpoint/ownership؛ المحاسبة وقيود أخيرًا في نافذة مستقلة مع بقاء سياسات الإرسال دون تعديل.
4) عند نقل DB: وقف كل writers بما في ذلك webhooks/jobs/الموظفون والواجهات التفاعلية القديمة؛ التقاط الأحداث في buffer متين معرف الهوية أو إثبات إعادة تسليم المزود قبل القبول، barrier/checkpoint نهائي ثم delta/restore/checks. لا ACK لحدث لم يُحفظ. تحويل اتصال كل writers إلى قاعدة واحدة، ثم فتح الجديد بمالك واحد لكل مجال. DNS وحده لا يسكت النسخة القديمة.
5) مراقبة auth/errors/latency/queue age وbacklog وdedupe وprovider reconciliation والأرصدة والملفات، ومقارنتها بخط الأساس. بوابات فقد/تكرار أو unknown outcome غير محلولة تمنع التقدم.
6) الرجوع قبل أي كتابة جديدة يمكن بتحويل المسار إلى القديم. بعد كتابة الهدف: لا رجوع أعمى إلى DB قديمة؛ إيقاف الكتابات ومصالحة الدلتا/عكس replication بطريقة مختبرة أو forward-fix. رجوع compute على نفس DB يتطلب توافق schema وسحب ملكية العمال أولًا.
7) الاحتفاظ بالبيئة والنسخ الأصلية طوال مدة رجوع تعتمد لاحقًا؛ لا حذف ضمن هذه المهمة. RPO=0 هدف مشروط بإثبات حاجز الكتابة والتقاط كل الأحداث؛ RTO يُقاس في rehearsal ولا يُضمن الآن.
أي تغيير/إعادة نشر في Emergent يجب أن يتبع AGENTS.md: prepare ثم prepublish من /app تحت lease المالك، ثم Deployment Succeeded أحدث وverify الناجح ثلاث مرات داخليًا. لا استعمال نجاح GitHub كإثبات نشر. إجراءات الإصدار الحالية لا تُعطّل؛ الاستضافة الجديدة تحتاج آلية هوية/تحقق مكافئة تُراجع قبل الاعتماد.
