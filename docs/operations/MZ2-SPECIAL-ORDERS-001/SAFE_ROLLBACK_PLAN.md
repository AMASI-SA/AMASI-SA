# خطة الرجوع الآمن — طلبات ميزان الخاصة

**الحالة: خطة موثقة وفاحص أدلة غير تشغيلي؛ الرجوع الفعلي لم يُقبل ولم يُنفّذ.**
المهمة `MZ2-SPECIAL-ORDERS-001`، 28 سبتمبر 2026.
لا توجد حاليًا نسخة رجوع معتمدة برقم إصدار وأدلة تجربة تشغيلية لهذه الميزة. أي قيمة مجهولة في سجل الأدلة تمنع الانتقال للنشر.

## 1. قاعدة القرار

**الرجوع يغيّر البرنامج، ولا يمحو ما حدث في العمل.**
لا يحذف طلبًا أو قطعة أو إيصالًا أو فاتورة مورد أو قيدًا صحيحًا، ولا يعيد مخزونًا خرج فعلًا، ولا يلغي تحصيلًا استلمه الموصل.
استعادة قاعدة بيانات أقدم إجراء تعافٍ من كارثة منفصل، وليست زر الرجوع البرمجي.

| الحالة | القرار الآمن |
| --- | --- |
| لم يُنشأ أي طلب خاص أو دليل أو حركة مرتبطة | قد تصلح النسخة السابقة بعد إثبات خلو **جميع** الأسطح من البيانات الخاصة، وتوافقها مع بقية الميزات الحديثة والعملاء. |
| توجد أي بيانات خاصة، ولو أُلغي الطلب أو تم توصيله | يمنع الرجوع إلى نسخة لا تقرأها. يلزم إصدار استرداد متوافق مع الهوية والمخطط والأدلة والعمليات الحالية. |
| الخلل في الإنشاء فقط | نوقف إنشاء الجديد، ونبقي الموجود ظاهرًا مع معالجة آمنة مثبتة. |
| الخلل في التحصيل/التكلفة/الخيارات/المخزون أو حدود المعاملة | نوقف الكتابات المتأثرة، ونترك القراءة والتدقيق، ولا نكمل العملية بنصف قيد أو نصف فاتورة. |
| النسخة المتوافقة غير متاحة أو غير مختبرة | نبقي الوظائف المتأثرة مقفلة ونصلح فوق الحالة الحالية؛ لا نفرض الرجوع إلى إصدار قديم غير متوافق. |

تصفير «الطلبات المعلقة» ليس دليلًا على صلاحية النسخة القديمة. يجب حفظ تاريخ الطلبات المنتهية والإيصالات والقيود وإمكان مراجعتها.
كما يمنع أن يعيد Commit جديد تنفيذًا قديمًا لميزة أحدث؛ سلامة تسلسل Git وحدها لا تثبت عدم التراجع الوظيفي.

## 2. ما هو موجود وما هو مطلوب

الموجود في المصدر: بوابات مغلقة افتراضيًا، قراءة مصدر ميزان، عقود حفظ ومعاملات Mongo حقيقية، سجل أحداث ومفاتيح منع التكرار.
`Enablement` في `binding.py` إعداد مكتوب يمرر إلى النسخة؛ **ليس زر إيقاف مركزيًا مثبتًا على كل العمليات العاملة**.

المطلوب قبل أي تفعيل: تحكم موثوق بصلاحية المالك، محفوظ ومدقق، مع رقم جيل كتابة `write_epoch`؛ تقرؤه جميع واجهات API والعاملين والطوابير والمهام والأجهزة المتصلة. يؤكد كل كاتب استلام الجيل، وتتحقق المحاولة المعاد تنفيذها قبل الالتزام أنها ما زالت مسموحة. تعذر قراءة الضبط = منع كتابة، وليس استئنافًا تلقائيًا.

التحكم يميز: إنشاء جديد، تحديث تشغيل قائم، كتابة مالية، إرسال أثر خارجي، والقراءة. إيقاف الإنشاء لا يطفئ قراءة الموجود. إيقاف المالية لا يسمح لمسار آخر أن يكتب خارج المعاملة. إذا كانت فاتورة أو تسوية مختلطة تضم طلب سلة وطلب ميزان، إما نجاحها كاملة أو منعها كاملة برسالة قابلة لإعادة المحاولة؛ لا نتجاوز الجزء الخاص بصمت.

**هذه ضوابط قبول للتنفيذ، وليست أسماء إعدادات أو نقاط API جاهزة.** لا تخترع متغير بيئة أو أمر pause/resume وتنفذه باعتباره معتمدًا. ضوابط المحاسبة العامة التي تطورها محادثة أخرى تحتاج مراجعة تكامل مستقلة دون تعديل قفلها.

## 3. إعداد نسخة الرجوع قبل التفعيل

تُحفظ هوية كل إصدار مصدر/نشر/شجرة/إصدار تشغيل، وإصدار الويب ونسخ تطبيق الموظفين و«تواصيل أماسي»، وقائمة القدرات ومخططات البيانات التي يقرأها ويكتبها. لا يكفي اسم Build أو رابط PR.

نسخة الرجوع بعد وجود بيانات خاصة يجب أن تتضمن قراءة كل الحالات السابقة والحالية، البوليصات الخاصة وصلاحياتها، معرفات MZ النصية وخيارات القطعة الحالية، مفاتيح منع التكرار والطوابير، وقراءة أرصدة المورد والبنك والموصل. المعالجة بعد الرجوع لا تُفتح إلا إذا نجحت اختبارات الكتابة على هذه النسخة تحديدًا.

يُحتفظ بنسخة متوافقة مع الميزة معطلة إنشاءً، لا بنسخة سلة فقط. قبل التفعيل تُختبر العودة إليها من المرشح على نسخة بيانات معزولة، بما فيها طلب قديم أنشئ بإصدار سابق وطلب أثناء كل مرحلة. الرجوع لا يعيد إسناد القطعة ولا يصدر بوليصة ثانية.

مرجع الإنتاج الذي شوهد في Git `a7bcb1626e2ad4defba2260d4a113417f91f3120` ليس هدفًا معتمدًا تلقائيًا. لا توجد في هذه الجولة معاينة للنسخة العاملة أو اختبار رجوع إليها. أي تغييرات أحدث للإنتاج يجب الحفاظ عليها أو إثبات سبب استبعادها، لا استبدال المشروع بأساس هذه المهمة التاريخي.

## 4. النسخ الاحتياطي والحفظ المالي

قبل التفعيل يلزم نسخة متسقة من قاعدة البيانات مع ملفات الأدلة الخاصة والبوليصات وسجل الأحداث ومفاتيح منع التكرار، ونسخة إعدادات مشفرة منفصلة عن Git. يجب أن تتطابق نافذة قاعدة البيانات مع الأدلة الخارجية، وألا تتغير النسخة بين الجرد والفحص.

نجاح أمر backup وحده غير كافٍ: تستعاد النسخة إلى بيئة معزولة، وتفتح الطلبات والملفات، وتُراجع قيود البنك والمورد والمخزون والموصل، ثم تقارن البصمات والأرصدة. يسجل المكان والإصدار والتاريخ وهوية من اختبرها. لا تُرفع هذه البيانات إلى المستودع؛ يوضع فيه مرجع دليل منقّح فقط.

هدف حفظ المعاملات الملتزم بها هو عدم فقد أي معاملة، لكنه **هدف قبول لا ضمانًا حاليًا**. زمن الاسترجاع يقاس بتجربة فعلية ولا يعطى تقديرًا غير مختبر. لا نفترض أن الخادم يستخدم Atlas أو أن استعادة نقطة زمنية مفعلة. التحقق من هذه الإمكانات مسؤولية مرحلة فحص البيئة قبل النشر.

Mongo يربط ضمان snapshot داخل المعاملة بشروط read/write concern؛ لا نستبدل جردًا متسقًا بعد إيقاف الكتابات بمجموعة استعلامات منفصلة قد ترى أزمنة مختلفة. المرجع: https://www.mongodb.com/docs/manual/reference/read-concern-snapshot/ . وإذا كانت البيئة Atlas فعلًا، تراجع شروط الاستعادة والإصدارات ونافذة الاحتفاظ: https://www.mongodb.com/docs/atlas/recover-pit-continuous-cloud-backup/ .

## 5. الاحتواء والجرد قبل تبديل الإصدار

1. يسجل البلاغ والمرشح والبيئة والمشكلة المحددة. يوقف إنشاء طلبات خاصة جديدة. تبقى الطلبات الحالية مرئية ولا تتغير مبالغها لإخفاء الخطأ.
2. يوقف نطاق الكتابة المتأثر ويُنتظر تأكيد كل كاتب لرقم الجيل وانتهاء المعاملات الجارية. يشمل ذلك retries وطوابير الأحداث وطلبات الأجهزة القديمة. لا تُقتل عملية أثناء أثر خارجي دون تحديد هل وقع الأثر أم لا.
3. يطابق ما تم في البنك والشحن والمورد والموصل مع الأحداث المحلية. نتيجة اتصال غير معروفة تُعلّق للمطابقة قبل تكرار الطلب الخارجي، ولا تعتبر فشلًا آمنًا لإعادة التنفيذ.
4. يجرد الجرد المتسق أدناه بعد وصول العمليات الجارية إلى صفر. أثناء مقارنة قبل/بعد تبديل الكود، يجب إيقاف **كل** كاتب يغيّر نطاق اللقطة، بما فيه طلبات سلة داخل جداول مشتركة؛ وإلا تكون المقارنة غير صالحة. وضع «وقف الجديد فقط» مختلف عن نافذة تبديل نسخة مضبوطة.

لكل سطح: العدد، مجموعة المعرفات المرتبة وبصمتها، وبصمة محتوى العمل الكامل بتسلسل ثابت. لا يكفي تساوي العدد أو الإجمالي؛ قد يتبدل قيد أو تختفي قطعة ويحل محلها سجل آخر.
تحتفظ المقارنة بحقول الهوية والمبلغ والحالة والخيارات والمراجع والتوقيت التجاري ونسخ المخطط والدليل. لا تستبعد حقلًا مؤثرًا بدعوى أنه متغير.
سجل إجراءات النشر الإدارية الجديدة يقارن منفصلًا؛ لا يسمح باستبعاده لاستثناء تغييرات تجارية. البصمات الكاملة تنتج داخل البيئة الآمنة؛ لا تنشر صفوف العملاء.

الأرصدة بالهللة للريال، ولكل حساب/طرف/حساب فرعي، مع المبالغ الأصلية وصور الصرف عند الحاجة. يجب تساوي مجموع المدين والدائن، وثبات النقد الفعلي والمورد والمخزون وعهدة الموصل ومستحقاته. يفحص عدم مضاعفة تحصيل أو أجرة أو ذمة أو فاتورة، وليس إجمالي المتجر فقط.

## 6. تنفيذ الرجوع المصرح ثم التحقق

هذا القسم يُنفّذ فقط بعد تفويض مالك مستقل مرتبط بالبيئة وهوية هدف الرجوع وأدلة التجربة.

قبل استخدام مساحة Emergent المشتركة يقرأ المسؤول `AGENTS.md` الحالية وحالة Release Guard من **تلك المساحة نفسها**:

```sh
cd /app
python scripts/production_release_guard.py status
```

القيمة المطلوبة `active=false`. قفل شخص آخر لا يُحذف. لا reset --hard ولا force-push ولا استرجاع عشوائي للمجلد.
تُتبع آلية Protocol v5 المعتمدة: المصدر A ثم بناء متكرر مطابق ثم intent-only B. لا يعاد استخدام intent لنسخة مختلفة أو ملف نتج في مساحة قديمة.
بعد أي تعديل مصدر أو دمج تكاملي تتجدد الهوية والفحوص؛ الموافقة على SHA قديم لا تنتقل تلقائيًا.

بعد نشر نسخة الرجوع يلزم إعلان Deployment Succeeded أحدث من العملية، والتحقق المعتاد:

```sh
python scripts/production_release_guard.py verify --url https://mezansalla.com
```

ثلاث قراءات متتالية بهوية المصدر/الإصدار المقصودة، critical hashes مطابقة، frontend مثبت، و`/build-meta.json` يرجع JSON الصحيح لا HTML. النجاح التقني للنشر لا يعيد الكتابات تلقائيًا.
تؤخذ لقطة بعدية داخل نافذة الإيقاف نفسها، وتقارن بجميع الأسطح والأرصدة أعلاه. لا إنشاء طلب أو إعادة قيد «للتجربة» داخل الإنتاج دون تفويض مستقل.

إذا أخفق أي فحص، يبقى النطاق المتأثر متوقفًا مع القراءة والدليل المحفوظ، وتجرى مصالحة/إصلاح متوافق. لا تعاد البيانات القديمة لإجبار الأرقام على التساوي.

## 7. فتح المعالجة والتفعيل التدريجي

التسلسل المطلوب: توافق القراءة والنسخة الاحتياطية أولًا؛ فحوص معزولة كاملة؛ إصدار إنشاء مغلق قابل للاسترداد؛ ثم تفعيل محدود ومصرح؛ ثم توسيع بعد قبول النتائج. يُختبر كل نوع طلب وطريقة تحصيل، لا مجرد البدل المجاني.

حدود توقف فورية: أي اختلاف مبلغ أو قيد مكرر؛ نقص خيارات/قطعة/فاتورة؛ مطالبة COD غير صحيحة؛ اختفاء طلب؛ تسرب إيصال/بوليصة أو قبول صلاحية مسحوبة؛ كاتب لا يلتزم بالإيقاف؛ فرق مخزون؛ عميل قديم يعرض قيمة خاطئة. لا ننتظر حدًا عدديًا أكبر للأخطاء المالية أو الأمنية.

يمكن معالجة الطلبات القائمة في النسخة المتوافقة فقط بعد نجاح فحوصها. فتح إنشاء الجديد قرار مستقل لاحق. تطابق SHA أو صلاحية القراءة وحدهما ليسا تفويض استئناف.
يُختبر أندرويد الموظفين وتطبيق الموصلين مستقلين، بما فيه النسخة القديمة الفعلية وQR/المعرف الطويل والبوليصة المحمية والجلسة. لا يصدر APK/OTA ولا يغير النشر في هذه الجولة.

## 8. قائمة تجربة الرجوع قبل القبول

- إنشاء مجاني وجزئي وهدايا وتصوير مع خيارات معدلة؛ عينات عند المراجعة والمورد والخدمات والتجميع والتوصيل والإغلاق والإلغاء.
- إيصال مرفوض ثم بديل، تحصيل متزامن، إعادة ضغط، انقطاع بعد وصول القيد وقبل رد API، وتوريد جزئي/صافٍ.
- فاتورة مختلطة ومخزون مرتبط وخدمات؛ تعطيل أثناء المعاملة ثم إعادة المحاولة. لا نصف عملية ولا تكرار.
- توقف كل الكتابات ثم محاولة جهاز قديم/عامل/مسار غير مباشر؛ يجب الرفض قبل الالتزام.
- نشر هدف الاسترداد المعزول ثم قراءة جميع الطلبات والأدلة؛ تجربة استئناف آمنة واستنفاد الطوابير بمفاتيحها القديمة.
- استعادة نسخة احتياطية في قاعدة **معزولة أخرى** ومقارنة البصمات؛ اختبار فرض فقد/تغيير قيد بنفس المجموع لإثبات كشفه.

تحفظ SHA/Tree للمرشح والهدف، وأسماء العملاء، والأوامر والنتائج وصور/آثار الاختبار المنقحة وتوقيع المراجع. لا نعلن نجاح هذه القائمة لأن اختبارات منفردة داخل النواة نجحت.

## 9. الفاحص المرفق وحدوده

`tools/rollback_gate.py` يفحص **ملف أدلة محليًا** قبل/بعد، ويرفض نقص الجرد، قدم اللقطة، هدفًا غير متوافق، فرق هللة، اختلاف هويات/محتوى، مخططًا أو عميلًا غير مدعوم، أو غياب مرجع اعتماد وتجربة.

```sh
python docs/operations/MZ2-SPECIAL-ORDERS-001/tools/rollback_gate.py evidence.json
```

النتيجة دائمًا `deployment_authorized=false` و`executes_changes=false`، حتى عند PASS.
الفاحص لا يتصل بالخادم ولا يوقف الكاتب ولا يثبت صحة/توقيع من زوده بالبيانات. التحقق المستقل من مصدر الأدلة شرط خارج هذه الأداة.
القالب `ROLLBACK_EVIDENCE.template.json` محجوب عمدًا؛ لا تملأ القيم بنجاح أو صفر بالتخمين. نافذة حداثة الفحص 900 ثانية إجراء فني للفاحص، وليست RTO موعودة.
**50 اختبارًا للوحدة تثبت فحوص هذا البرنامج فقط، لا جاهزية الرجوع التشغيلي.**

## 10. التعافي من كارثة قاعدة البيانات

عند فساد بيانات فعلي يحتاج القرار موافقة منفصلة وخطة استعادة ومطابقة. تحفظ الحالة الحالية والقيود والأدلة قبل الاستعادة، وتستعاد نسخة إلى بيئة معزولة أولًا، وتحصر الفجوة منذ نقطة النسخ، ثم تطابق طلبات سلة والبنك والشحن والمورد وما وصل فعليًا للعملاء.
لا تصبح دفعة العميل غير مدفوعة لأن نسخة قديمة لا تعرفها؛ ولا يُعاد شحن طلب سبق تسليمه. القيود التصحيحية أو العكسية مرتبطة بسبب حقيقي وبالمستند الأصلي واعتماد محاسبي، لا بحدث نشر الكود وحده.
