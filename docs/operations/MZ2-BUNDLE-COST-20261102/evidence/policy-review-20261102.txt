Supplement: functional impact of converting a service resource binding to direct

This is a further read-only trace, not an instruction to convert the live binding.
Non-stock classification must not be equated with absence of preparation or
supplier-accounting work. No additional tests were run.

1. Shared cost and resource usage identity
product_option_cost_routes._binding_view() resolves mode=resource from the shared
resource unit_cost and binding quantity. update_component_cost() updates that
shared resource, audits resource_cost_changed, and counts dependent bindings.
component_workspace() lists resource-backed product usages only. A direct binding
uses a fixed direct_amount, no longer follows that resource's future reference
cost, and disappears from its resource-backed usage list. The shared resource
record itself is not deleted by save_option_cost().

2. Physical inventory
stock_component_consumption_service derives demands only for mode=resource and
skips resources with kind=service or track_inventory != True. Tracked components
use resource_id for stock lots, reservations and movements. A direct binding
does not participate in that path. bundle_fulfillment_v2.allocate_leaves() marks
direct_cost leaves ready with no physical allocation; its cost_only source-change
guard prevents converting such a leaf into a stock/supplier obligation later.

3. Preparation services and supplier eligibility (material)
preparation_piece_line_services._line_service_context_for_batch() selects only
mode=resource option bindings, loads their resource IDs, and calls
preparation_piece_operations.inherit_required_services(). That function inherits
kind=service for a matching option/value and writes service_id=resource_id,
reference_unit_cost, quantity, customer_selected=True and status=pending.
Crucially, inherit_required_services() does NOT check requires_preparation.
Therefore requires_preparation=False alone does not establish that removing the
resource binding preserves all service-plan behavior. The service may still be
inherited for a piece whose preparation was triggered by another requirement.
build_duration_history() also keys service combinations by these service IDs.

supplier_category_service_policy validates supplier service_ids against active
kind=service/non-stock resource IDs and snapshots their costs and preparation flag.
supplier_native_invoice_v2 validates each invoice service_id with require_source()
and resolve_debit(..., 'service', service_id) before constructing service debits.
These are real service identity/accounting paths. This review did not establish
that the particular live embroidery resource is currently used by any supplier
or posted invoice. Changing the option binding does not directly rewrite those
stored financial entries, but removes this source for later service-plan creation.

4. Quantity scope
The direct_cost option leaf uses binding.quantity times the expansion multiplier.
It does not use the current_product per_unit component scope branch. For one
physical current_product per sale unit and binding quantity 1 the quantities
align, but conversion is not a general semantic substitute if a recipe later
contains multiple current_product units/slots.

5. Historical evidence
Existing bundle intake and frozen definition metadata retain their original
resource/binding data and prices. capture_intake() skips already captured line
IDs; no option-binding update directly edits stored order snapshots or journals.
Direct conversion is not a historical repair. New or still-unfrozen estimates
would use the changed catalog representation. capture_actual_cost() uses a ready
cost-only leaf's frozen unit_cost; tracked resources instead use stock cost
state or a posted receipt according to their sourcing mode.

6. UI/model evidence to inspect before classifying the live service
ProductOptionCostEditor.jsx explicitly distinguishes 'مكوّن مشترك' (mode=resource)
and 'مبلغ مباشر' (mode=direct), and shows the selected shared resource and price.
MezanComponentsProduction.jsx labels non-stock rows 'خدمة عمل'. Its edit form
exposes 'تمنع شحن المنتج حتى تكتمل الخدمة' for requires_preparation; this is an
operational flag, not the same as track_inventory. The UI says it is enabled
automatically for newly created preparation services such as embroidery.
mezanComponentCatalog.js sends both kind/track_inventory and requires_preparation.

For the actual live row, establish mode, resource_id, kind, track_inventory,
requires_preparation, shared product usages and relevant supplier/service-plan
usage. A blank/false preparation flag plus non-stock type is useful evidence
but not complete proof of cost-only use because the inheritance function above
does not filter on that flag. Do not infer origin=inhouse from a service label.

Conclusion of the supplement
The direct path is a legitimate monetary-cost model, but conversion is not a
semantically neutral repair for an existing shared service resource. It can
remove central tariff propagation, service identity, preparation inheritance
and later supplier-invoice eligibility. Keep the existing resource until the
actual desired workflow is known; do not convert solely to avoid provenance.
The executor question is not universal for every standalone service expense,
but unresolved operational provenance is real for the present resource model.
