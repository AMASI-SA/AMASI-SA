# Owner-triggered Merchant product observation contract

Design checkpoint, not an attached route. Base M7 `2fba251ab73780d984b2c53a4f991bc98d61c441`. Assessment: `5813304637c2873ebebb213009977046fb50edcd`. Retail Source A `e16b46f0453776f5bb471ae1e641a083af275c38` is frozen and remains separate.

## Reachable owner flow and authorization seam

Proposed read endpoint: `GET /google_ads/merchant-products/observation?account_id=...&merchant_id=...`. It runs only on an explicit owner action. It does not select/switch an account, save a mapping, change a campaign or start a background reader. Root owns its eventual router attachment and UI assignment.

The server must derive the owner with the existing authenticated `principal`; reject staff and disabled actors. Both numeric IDs are explicit selections, never defaulted from environment, registration configuration, the first returned account, or an AI assertion. Require unique connected `api_connection` rows for that exact owner/provider/account, plus connected provider projections. Missing, duplicate, conflicting or unreadable membership is unproved. An explicit request selects the read target; it does not alter `mezan_selected` or any owner's existing preference.

Use an opaque server-created bound read session, not request fields such as `verified:true`. It must bind the same owner, Google subject, granted Adwords+content capabilities, selected Ads customer, selected Merchant account and credential observation to the read transports. Verify the actual Ads customer via existing account metadata. A fresh complete native `product_link` read must contain the selected Merchant account, validate every returned resource under the selected Ads customer, and reject malformed/duplicate/truncated link observations. Discovery alone is insufficient. Merchant access must succeed for that exact account; accessible manager/parent IDs cannot silently substitute for the selected child.

Recheck server membership and the bound credential observation before returning data. Revocation, relink, changed scopes/subject/account selection or unknown validation discards the observation. This is bounded read isolation, not a claim of atomic external account or catalog state, nor proof of uninterrupted history. Credential material, HTTP authorization headers, provider error bodies and raw page tokens must never enter output, persistence or logs.

**Current missing shared interface:** `google_merchant_registration._fresh_google_context` is a registration-specific helper that enforces a configured developer email. Do not reuse it for this generic route. `google_ads_reporting._credential` uses the existing CAS refresh writer but returns only an access token; `account_client` computes an epoch with a later credential read. This does not establish that token and epoch come from the same observed grant across relink. Do not extract `GoogleAdsClient.headers` or invent a second refresh implementation. Root must assign a narrow opaque bound-session interface to the existing credential owner before real provider wiring. No new OAuth scopes or registration action is requested. This work does not claim that historical connected projections are an atomic OAuth account snapshot.

### Proposed additive helper in the existing credential boundary

Root proposes a later narrow additive helper in `google_ads_reporting.py`, with existing `_credential` callers/signature and OAuth writers unchanged. The helper first calls the current safe-refresh path, then reads a fresh PRIMARY/majority `CREDENTIAL_REFRESH_PROJECTION` snapshot. Inside that private boundary it must compare the returned token to the decrypted access token of that exact snapshot using a constant-time comparison, validate the same subject, required scopes and useful expiry, and fail closed on unreadable/conflicting evidence. An access token plus a separately read epoch is never enough.

The helper should expose an opaque read-session/factory with an opaque nonsecret evidence ID. Its private closure retains the full credential snapshot with absent-versus-null semantics, including grant/token revision fields when present. The factory can construct the existing Ads client and the fixed-host Merchant read transport from the same bound token without returning it or scraping headers. Before requests and before results escape, a PRIMARY/majority exact-snapshot read must confirm no change; concurrent safe refresh may conservatively invalidate the observation. Bind owner/account membership separately before and after. No output or exception repr may serialize the closure, snapshot or credentials. This proves an observed bound interval subject to the read checks, not historical writer exclusion or an atomic cross-provider snapshot.

The helper requires root's explicit shared-file assignment and independent race tests: old token after relink, refresh acknowledgement unknown, token/snapshot mismatch, changed scope or subject, absent-to-null/revision changes, concurrent refresh and revoke. The observer module remains independently testable with fake streams; real route wiring cannot bypass this seam.

## New observer module and limits

Owned implementation paths are `backend/integrations_control_center/google_merchant_product_observation.py`, `backend/tests/test_google_merchant_product_observation.py`, and this task's new operations documents. Existing router, auth, catalog, retail and inventory files remain untouched. The observer may be implemented and tested with an injected authorized streaming read transport; it cannot independently prove the caller's authorization and will not advertise it as proved.

The module itself constructs only the fixed `https://merchantapi.googleapis.com/products/v1/accounts/{selected_account}/products` GET endpoint, with an empty body and stable page size. No caller URL, redirect following, landing-page fetch, token acquisition, write endpoint, retry or account discovery. Require bounded streaming bytes before JSON parsing, bounded whole traversal time, page/row limits and safe typed errors without provider payloads. A caller-created scope object is a request binding, not an authorization certificate.

Validate all rows, including ones that will not later match a store product. Keep the complete native account, local/online distinction, language, feed label and offer ID; validate explicit fields against the v1 native `name` and optional unpadded `base64EncodedName`. Keep `dataSource`, version and the separately typed `link`, `canonicalLink`, `mobileLink`, `adsRedirect`, and `itemGroupId`. Do not collapse feed/language/account rows by offer ID, normalize SKU case, infer parent/variant identity or silently discard an unidentified row. Do not parse v1 names as v1beta names. Validate encoded special identifiers against explicit fields rather than trusting a naive delimiter split.

Pagination follows `nextPageToken` even after short/empty pages. Reject repeated tokens, malformed tokens/pages, foreign resource/data source scope, duplicate native identities, invalid row shapes and any resource bound exceeded. Incomplete observations must not expose a usable partial product set. Successful traversal means only that all pages returned for this bounded request were consumed; `atomic_snapshot:false` must remain explicit. Empty successful pages are not provider/owner identity proof.

Return immutable typed product observations with a semantic digest independent of timestamps and input ordering; include observation start/end separately. The native link fields are observations, not verified destinations. Keep `mapping_status:unverified`, `store_product_mapping_verified:false`, `category_membership_verified:false`, `attribution_verified:false`, `execution_authorized:false`, and provider writes zero. A native Google Ads eligibility state can lag provider changes; this endpoint neither reads nor promises instantaneous Ads eligibility.

## Source boundary for a later matcher

The seasons agent's independent inventory assessment requires explicit native empty options and variant aliases **plus complete native variants pagination** before proving no variants; normalized zero counts and bounded stored detail evidence are insufficient. Root will assign that capability separately. This observer makes no stock/simple-product claim and does not alter M7 inventory proof. Salla `urls.customer` must come from authenticated native details with exact owner/store binding; shared canonical URLs, SKU/title, item group IDs and section URLs remain insufficient for variant or category mapping. No arbitrary URL verification request is introduced.

## Functional acceptance before integration

* Successful multi-page read preserves distinct feed/language identities and every independent link/grouping field; shuffled rows retain semantic digest while observation times remain separate.
* Reject wrong account/resource/data source, v1beta names under v1, inconsistent encoded names, invalid local/channel marker, missing identity, duplicate rows, malformed link fields and malformed unknown rows that might otherwise disappear. Preserve valid query-bearing links exactly; query stripping cannot establish identity.
* Test Unicode and special offer IDs from explicit native fields; no SKU/title/casefold inference. Retain raw native link strings only within a documented bounded representation; never fetch or execute them.
* Enforce byte/page/row/total-time bounds, invalid/nonfinite/duplicate-key JSON, late stream failures, HTTP rejection, redirect refusal, repeated token cycles and short pages with a next token. Error output contains no tokens, body fragments or exception repr.
* Auth integration tests must later prove owner-only access, cross-owner and foreign Merchant refusal, complete native link scope, relink/revoke/change during traversal, and no raw credential escape. The pure observer tests do not stand in for this unresolved shared interface.
