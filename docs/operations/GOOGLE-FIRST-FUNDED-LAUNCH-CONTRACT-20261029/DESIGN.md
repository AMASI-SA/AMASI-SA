## Initial assessed PAUSED-first approach

The initial PAUSED-first proposal was a complete **owner launch-authorization and per-campaign qualification** vertical, with persistence, review UI, revocation and explainable blockers. Do not yet add a funded provider dispatch or release the no-resume blocker. This produces a usable owner decision surface while preserving the unresolved native stop-history condition instead of inventing a trusted boolean that no real reader can produce.

The owner supplies explicit numeric limits; empty fields remain empty and saving cannot activate anything. Natural-language commercial guidance, product evidence, a category URL, an account connection, passing tests and a successful technical Mongo probe do not authorize spending. The owner can review a saved grant and see exactly why a specific PAUSED campaign is not qualified. Saved grants default to inactive/pending prerequisites, not effective authorization. Activation is a separate explicit owner action after genuine prerequisites pass.

A new dedicated grant avoids weakening creation's PAUSED-only contract or rewriting the six existing policy handlers. A typed grant mutation participates in the same account epoch; no generic adapter fallback or reusable capability token. New namespace permissions/indexes/legacy shape are an additional production prerequisite. Existing six handlers remain unchanged in this next patch.

## Native owner-stop/history blocker

Current PAUSED plus Mezan origin is compatible with a campaign that an owner enabled externally and later paused. A permanent application journal can prove **Mezan never submitted a launch**, not that nobody launched/stopped it through Google or another integration. A synthetic `never_launched:true`, an empty local history list or a newly added marker on an old campaign cannot close that gap.

Official Google Change Event documentation states a 30-day query window, at most10,000 rows per query and possible three-minute delay; it also warns that not every change shown in web Change History is included and that Google Ads Editor changes are unsupported. Therefore a negative Change Event query cannot alone prove no owner stop. Reference: https://developers.google.com/google-ads/api/docs/change-event (reviewed 2026-10-29). A fresh complete change-status snapshot likewise describes observations, not a provider-side atomic compare-and-set fence.

Even a documented complete historical window would leave the last-read-to-send external-writer race; the current API update is not a shared writer epoch across Google UI, other clients and Mongo. The contract must not silently assume exclusive external ownership. Qualification stays blocked when history/source coverage or the latest stop state is unknown. An enforceable exclusive-control/provenance mechanism or another explicitly reviewed product contract is required before claiming strict automatic no-owner-stopped-resume acceptance. Existing authenticated manual owner actions are a separate deliberate action, not an automatic fallback.

Application-side stop controls can be reliable: introduce a durable per-identity stop/tombstone generation and record an owner stop even if native status is already PAUSED. A stop/revoke before the launch floor must defeat its epoch/proposal CAS. After a positive floor ACK the request is explicitly in flight; a stop should produce a separate safe pause workflow, never pretend that a sent request was canceled. External no-op stop intent remains unobservable; do not promise otherwise.

## Updated primary alternative: atomically create a new ENABLED campaign

This is the recommended next useful funded vertical, subject to root contract review and real owner limits/storage prerequisites. Do not first create a PAUSED campaign and later issue enable. Instead construct one owner-approved **brand-new** Search/RSA campaign/budget/ad-group/ad/criteria/correlation graph and create it ENABLED in one `GoogleAdsService.Mutate`, `partialFailure:false`. No campaign exists before this one request, so this operation cannot resume an existing owner-paused resource. It does not need to infer the unknown earlier history of an existing PAUSED campaign.

Official v25 `GoogleAdsService.Mutate` supports atomic transactions across supported resource types and negative temporary references; all operations succeed together or fail. Temporary IDs are not remembered across requests. Official sources reviewed 2026-10-29: https://developers.google.com/google-ads/api/reference/rpc/v25/GoogleAdsService/Mutate and https://developers.google.com/google-ads/api/docs/mutating/overview . This provider atomicity does not make Mongo and Google one distributed transaction and does not authorize retry after an ambiguous response.
