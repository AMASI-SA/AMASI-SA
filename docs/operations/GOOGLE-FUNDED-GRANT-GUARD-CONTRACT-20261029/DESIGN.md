## Canonical account and supplied grant boundary

The pure grant's decimal1..20 account pattern matches the existing draft syntax and accepts leading zeros. It is a bounded supplied string, not native account verification. The producer must obtain the account from the tenant-owned linked projection and current native metadata, requiring exact `str(customer.id)==customer_id` and currency/timezone consistency. The current `GoogleAdsClient.account_metadata` already rejects aliases that fail that comparison. Do not strip leading zeros and guess ownership or infer it from the pure graph. Display formatting may be normalized by the existing identifier helper before the verified lookup; persist/hash only the canonical verified identity. Account formats and test fixture123 are not evidence of an actual Google account.

The owner HTTP body cannot supply reviewed_by, user_id, native proof flags, activation state, operational claim, consumed markers or an arbitrary owner_review_digest. Derive persisted owner/tenant through current authenticated owner lookup. Rebuild the exact server draft and review display (scope, budgets, currency, dates, product/URL/template, graph hash, budget semantics); compare a supplied expected review digest with that canonical review and derive the stored digest on the server. A digest is integrity binding, never authentication. Financial fields have no defaults; missing amount/cap/expiry or stale review blocks save/activation. A missing margin/ROAS target remains unknown.

Save may persist configured/inactive review; explicit activation must require the complete installed executor/storage/native prerequisites. Installation or later flags cannot activate old configuration. With runtime false, activation is unavailable, not silently deferred as a future effective grant. OAuth-independent revoke remains available to the current authenticated owner under healthy supported Mongo, without native reads or execution flags. Existing six policy handlers remain unchanged.

## Typed common-transaction commands

No optional adapter, nontransaction fallback or public generic command endpoint. The same owner must implement these narrow guard branches and the corresponding trusted grant/authority helpers.

1. **`FundedGrantMutation`**: save/activate/revoke with exact grant_key, expected revision, server-derived actor/review binding and allowlisted public values. Reload current grant and account guard in one session; CAS revision and account epoch together. Revoke only disables future permission and preserves private run/claim/consumed/quota/hold fields. Activation records current owner review, valid interval, applicable policy presence/revision/digests and verified metadata/configuration binding; it is not itself a reservation or reusable dispatch token. A concurrent existing policy write or grant revoke participates in the same epoch.
2. **`FundedNewCreationReservation`**: synchronous decision using the exact prepared pure intent plus trusted earliest native/product/auth bundle, not model/client flags. Reload active current grant, stable slot/journal absence or consumed status, applicable standing/creation policy presence/digests, original service proposal and account native fence. Recheck owner grant/time/currency/budget/scope, exact enabled graph, current product/settings evidence and complete bounded native inventory; reserve common exposure and persist funded journal/private grant claim/proposal linkage/quota/epoch in one TX. Require the exact account fence to be positively claimed before this operation; write a marker on that fence in the TX. No provider request can follow an unknown acknowledgement.
3. **`FundedNewCreationDispatchFloor`**: reload current active grant/revision/owner_generation/review/expiry, exact journal/claim/allocation/graph/proposal and native fence. Rebind current applicable policy snapshot and application stop generation. Write proposal submitted/claim/graph marker, permanent consumed submission identity and common epoch atomically; fence marker also participates in the write conflict. Raw commit exactly once, with retained bounded original-task lifecycle/deadline and fresh precommit expiry. Positive ACK first is logical in-flight work; grant revoke, application stop or proposal cancellation first must block HTTP. Unknown ACK yields no provider request and retains original hold/fence/consumed evidence; receipt readback is not fresh permission.
4. **`FundedNewCreationSettlement`**: server loads original exact proposal/operation graph/receipt/correlation and independently verified resource mapping/readback. Positive original campaign+budget identity binds the pending allocation; known terminal no-HTTP or known provider atomic rejection is distinguished from unknown transport. Update journal/claim/allocation/epoch atomically; do not refund quota. No absence, timeout, session cleanup or missing change-history entry is a release proof. Unknown remains held and unrepeatable across restart.

Current guard snapshot reads of owner/product/OAuth/analysis are not serialization against their writers. Revalidation detects observed drift; do not claim this proposal creates a shared metadata/external Google writer fence. Policy/grant/stop/proposal/fence writers named above must actually join the new epoch/CAS boundary. All existing scopes/financial limits remain enforced when a new resource is added.

## Exposure and no double counting

A new funded campaign is different from an existing owned PAUSED campaign. Its amount is one new unbound pending hold until original native identities are proved. Combine the explicit grant's account/campaign caps with every applicable present owner policy conservatively; missing policies are proved absent by bounded reads, never fabricated. A legitimate grant-only account does not require inventing a standing or PAUSED creation policy. Ambiguous present limits, currency, legacy shapes, shared resources or unresolved ownership block.

After positively mapping the original campaign+budget pair, count one maximum for that exact pair across native ENABLED amount, retained original funded hold, original PAUSED hold if any proved lineage actually applies, and pending standing target. Do not add a reflected funded hold to its native budget again. Before mapping, a matching campaign name or label alone cannot justify deduplication; retain the unbound hold conservatively and block competing account work. Existing PAUSED allocation is never upgraded by this new-create mode. Foreign budget drift can raise conservative exposure but grants no authority, manual adoption or release. REMOVED release needs positive original resource proof.

## Prepared auth and actual native dispatch consumer

The future gateway obtains/refreshed OAuth and constructs a prepared fixed-header client **before** final native/product validation and reservation/floor. Pin canonical customer/auth_epoch and earliest proof timestamps; validate sufficient token lifetime for bounded floor+request or refresh before restarting the proof bundle. Current inspected `account_client` awaits `_credential` before constructing `GoogleAdsClient`; current `request` uses captured headers and one HTTP stream. Arbitrary wrappers may refresh later; no universal prepared-auth claim is made.

After positive floor ACK, the actual chosen client path must permit only synchronous flags/expiry/native-age checks followed by the single `mutate` await. No intervening account_client/client construction, OAuth refresh, DB/audit, product/native read or validate-only call. Test the actual adapter/transport with a sentinel that fails on postfloor refresh/intervening work; check relink/token expiry and unknown responses. HTTP401/403 must not trigger token refresh plus an automatic resend. Mongo and Google are not one transaction; unknown request is retained, not retried.

The native payload is exactly one new ENABLED Search/RSA graph with partialFailurefalse and no existing mutable targets. Preview validates those exact bytes without mutation. Original temp-to-native response positions plus correlation and independent readback prove ownership; labels/temp names are not idempotency keys. A campaign externally paused after creation is never re-enabled to make readback match. Stop after floor ACK is a separate safe stop workflow once the original resource is identified, not retroactive cancellation of the create. New worker/gateway must consume these helpers; no paid route or worker is implemented in the next storage step by implication.
