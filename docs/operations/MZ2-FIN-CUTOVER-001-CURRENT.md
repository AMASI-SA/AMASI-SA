- لا يستورد أو يرحل أو يعيد إنشاء أو يعيد ترحيل أي قيد أو حركة مالية
  تاريخية من ميزان القديم.
- تمثل الحالة السابقة للقطع بمجموعة أرصدة افتتاحية واحدة، متوازنة ومدعومة
  بأدلة غير Legacy.

- التاريخ المالي والأرصدة والقيود والأدلة من ميزان القديم ممنوعة دائمًا.
  يسمح فقط بتعريف/إعداد غير مالي كمسودة غير معتمدة تحمل provenance؛ وبعد
  مراجعة المالك يصبح إعداد ميزان 2 جديدًا ولا يصبح دليلًا ماليًا.

## مسار الاستكمال دون تدخل مالي

1. أكمل بوابة تنفيذ P01 وفق مراجعة وسياسة المستودع.
2. ابنِ P02 إلى P08 بالتتابع وفق بوابات التنفيذ، مع الاختبارات، دون Publish
   أو كتابة Production مالية. استخدم `QUEUED` قبل بدء كل مرحلة و
   `IN_PROGRESS` بعد بدء عملها؛ لا تدّعِ أنها منفذة مسبقًا.
3. يجب أن يتضمن المصدر حاجز Backend مركزيًا يمنع جميع كتابات القيود
   العادية والبديلة قبل `safe_active`، ومسارًا افتتاحيًا وحيدًا محكومًا،
   ومجموعات ذرية، وقراءات operation-scoped، وقيد طلب مكتملًا.
4. بعد اكتمال جميع بوابات التنفيذ، ثبّت source commit A النهائي قبل الدمج
   النهائي وشغّل البناء/التجميد المحكوم من A.
5. أنشئ commit B ابنه المباشر ويغير
   `release/release-intent-v5.json` فقط، ثم شغّل CI وراجع A/B.
6. ادمج مع الحفاظ على A وB دون squash أو rebase، وادفع لتشغيل Release
   Readiness، ثم توقف بانتظار موافقة Publish. لا تنفذ `prepare` أو
   `prepublish` قبل الموافقة.
7. بعد موافقة Publish المنفصلة للهوية نفسها، نفذ `prepare` ثم
   `prepublish` وانشر الحزمة مرة واحدة وهي خاملة ماليًا،
   ثم نفذ Release Guard verify واختبارات Production غير المالية.
8. اجمع أدلة الأقسام الثمانية وأنشئ المعاينة. لا ترحلها دون تفويض مالي
   صريح مستقل.
9. بعد ترحيل القيد الافتتاحي والتحقق منه، يجب أن يصبح
   `safe_active=true` قبل السيناريو 6 وقبول P08.

## عقد الحالة

نجاح الكود أو CI أو الدمج لا يجعل المرحلة `COMPLETE`. تستخدم
`RUNTIME_ACCEPTANCE_PENDING` حتى نشر Runtime وقبوله. لا تصبح المرحلة
المالية `COMPLETE` قبل قبولها بعد `safe_active=true`.
