## قرار التنفيذ المرحلي المعتمد

التنفيذ مقسم إلى مراحل إلزامية لا يجوز دمجها في دفعة واحدة:

1. **P0 — Salla Contract Evidence:** إثبات عقود إنشاء وتعديل وحذف عناصر
   الطلب وقرار فرق المبلغ باستخدام Sandbox أو mocks رسمية فقط. لا Product
   code ولا كتابة على Production.
2. **P1 — Reconciliation and Completeness Protection:** Backend فقط؛ operation
   model وidempotency وper-order lock ومطابقة قراءة فقط وcompleteness snapshot
   وحارس مركزي للانتقالات النهائية. لا Salla writes ولا Mobile UI ولا OTA.
3. **P2 — Zero-difference item add/edit:** لا تبدأ دون موافقة جديدة؛ إضافة
   وتعديل فرق المبلغ فيها صفر مع Workflow مستقل وواجهة تطبيق أماسي.
4. **P3 — Positive difference:** بعد إثبات واعتماد مسار الدفع.
5. **P4 — Negative difference/refund:** بصلاحية وFeature Flag مستقلين.
6. **P5 — Post-supplier revision:** supplier file versioning وinvalidation
   وhold وacknowledgment.

يجب التوقف بعد P0 وP1 وتسليم الأدلة وPR الحماية؛ لا merge ولا Production
deploy ولا OTA دون موافقة صريحة.

## ملخص المراجعة المرجعية المعتمدة

- Salla هي المصدر التجاري والمالي والمخزني؛ لا ينشأ order item مالي محلي
  قبل نجاح Salla ثم إعادة Fetch ومطابقة النتيجة.
- Salla توثق Order Items APIs للإنشاء والتعديل والحذف، لكن السماح حسب حالة
  الطلب، وسلوك الطلب المدفوع، وفرق المبلغ يجب إثباته في P0 ولا يستنتج من
  وجود Endpoint فقط.
- `unified_orders` و`order_review_workflows.items` و
  `mezan_preparation_pieces_v1` قد تختلف إذا تغيرت عناصر Salla بعد تجميد
  Workflow؛ لا توجد completeness gate مركزية مكتملة حاليًا.
- `POST /fulfillment-v2/batches/{batch_id}/handoff` يحتاج حماية صريحة من
  snapshot حديثة ولا يجوز أن يستدعي Salla synchronously أثناء handoff.
- `order_adjustments` الحالي لا يقدم versioning/audit كافيًا للـvariant
  والخيارات وcustom fields.
- نظام تعليمات خدمة العملاء الحالي يعاد استخدامه كما هو معماريًا عبر
  `scope`, `target_ids`, `target_stages`, `enforcement`, و`operational_hold`.
- واجهة الإضافة والتعديل ستكون في صفحة تفاصيل الطلب وبطاقة المنتج داخل
  تطبيق أماسي، مع صلاحيات Mobile مستقلة لا تمنح وصول Mezan Web.

# 1. الهدف

تنفيذ مسار آمن ومتكامل في **ميزان Web والـBackend** لخدمة العملاء يتيح:

1. إضافة قطعة/منتج تجاري جديد إلى طلب قائم قبل حالة `تم التنفيذ`.
2. تعديل خيارات العميل لمنتج موجود داخل الطلب.
3. إبقاء **سلة** المصدر التجاري والمالي والمخزني للطلب.
4. إدخال القطعة الجديدة في Workflow مستقل يبدأ من `pending_review` دون إعادة بقية المنتجات إلى الخلف.
5. منع إغلاق أو شحن الطلب إذا كانت أي قطعة حالية في سلة غير ممثلة في Workflow والقطع التشغيلية أو لم تكمل مراحلها.
6. حفظ Versioning وAudit كامل لخيارات العميل وإبطال ملفات المورد القديمة عند تغير المواصفات.
7. إعادة استخدام نظام تعليمات/تنبيهات خدمة العملاء الحالي بدل بناء نظام مكرر.

# 2. نتائج المراجعة السابقة التي يجب تأكيدها على Production

هذه نتائج تشخيصية سابقة، وليست بديلًا عن التحقق على أحدث Production:

- الطلب محفوظ في `unified_orders`.
- Workflow الطلب في `order_review_workflows`.
- هوية المنتج داخل الطلب هي `order_item_id`.
- كل وحدة كمية يمكن أن تصبح `piece_id` في `mezan_preparation_pieces_v1`.
- نظام التعليمات الحالي يدعم `scope = order | item | piece` و`target_stages` و`enforcement` و`operational_hold`.
- لا يوجد حاليًا مسار متكامل مثبت لإضافة `order_item` تجاري مدفوع إلى طلب قائم.
- الموجود باسم `operational-items` ليس منتجًا ماليًا ولا يضاف إلى سلة.
- تغير عناصر سلة بعد تجميد Workflow قد يسبب اختلافًا بين:
  - `unified_orders.products`
  - `order_review_workflows.items`
  - `mezan_preparation_pieces_v1`
- تعديل خيارات العميل بعد اعتماد المراجعة لا يملك Versioning/Invaldiation مكتملًا لملف المورد.
- يجب تدقيق مسار `POST /fulfillment-v2/batches/{batch_id}/handoff` والتأكد أنه لا يتجاوز الحواجز التشغيلية.

أثبت أو صحح كل نقطة في ملخص التسليم النهائي مع ذكر الملفات والدوال والأسطر الحالية.

# 3. القاعدة المعمارية الأساسية

## سلة هي المصدر التجاري والمالي

أي إضافة أو تعديل تجاري يجب أن يتبع التسلسل:

```text
Mezan Web
→ Mezan Backend validation
→ Salla write
→ Salla success confirmation
→ Fetch order again from Salla
→ Resolve stable source item identity
→ Sync/reconcile Mezan
→ Create/update workflow and pieces
```

ممنوع إنشاء `order_item` مالي محلي في ميزان قبل تأكيد نجاح سلة.

إذا كانت Salla API لا تدعم عملية معينة على طلب قائم، لا تنشئ محاكاة مالية داخلية. استخدم مسارًا آمنًا موثقًا مثل طلب تكميلي أو رابط دفع مرتبط بالطلب الأصلي، مع بقاء المصدر المالي في سلة.

# 4. مرحلة التحقق من Salla API

قبل التنفيذ، تحقق من الكود الحالي ووثائق Salla الرسمية وحدد بالدليل ما تدعمه API للطلب القائم:

1. إضافة سطر/منتج جديد.
2. تعديل Variant أو خيارات منتج موجود.
3. تغيير الكمية.
4. تغيير السعر.
5. حذف منتج.
6. تحصيل فرق المبلغ أو إنشاء رابط دفع.
7. التعامل مع فرق سالب/استرداد.

أضف مستند Evidence داخل PR يحتوي لكل عملية:

- Endpoint أو SDK المستخدم.
- هل العملية مدعومة على طلب مدفوع/قيد التنفيذ.
- القيود النظامية.
- شكل الاستجابة.
- خطة fallback إذا لم تكن مدعومة.

لا تستخدم Production orders في التجارب. استخدم mocks أو Sandbox/بيئة اختبار متاحة.

# 5. إضافة قطعة من تفاصيل الطلب

## واجهة ميزان

أضف زرًا على مستوى الطلب داخل تفاصيله:

```text
إضافة قطعة
```

يفتح نموذجًا يدعم:

- البحث في منتجات سلة بالاسم أو SKU.
- اختيار المنتج.
- تحميل الخيارات الفعلية للمنتج من سلة.
- اختيار Variant.
- تحديد الكمية.
- عرض المخزون.
- عرض السعر المؤكد من سلة.
- حساب فرق المبلغ.
- عرض حالة الدفع.
- تأكيد الإضافة.

## حارس الحالة

الإضافة مسموحة فقط قبل `تم التنفيذ` حسب سياسة حالات صريحة في Backend.

لا تعتمد على إخفاء الزر فقط، ولا على مقارنة نصية هشة للحالات.

مثال خطأ Backend:

```json
{
  "code": "order_item_addition_not_allowed_after_completion",
  "message": "لا يمكن إضافة قطعة بعد تم التنفيذ."
}
```

حدد الحالات المسموح بها والممنوعة في Policy مركزية قابلة للاختبار.

# 6. خيارات العميل الديناميكية

المقصود خيارات سلة الفعلية، مثل:

```text
المقاس: طويل / عريض
اللون: أحمر / أخضر / أصفر
هل تريد إضافة اسم؟ نعم / لا
```

```text

```

```text

```

ويصبح Required قبل الحفظ.

إذا اختار:

```text
لا
```

يجب:

- إخفاء الحقل التابع.
- مسح القيمة السابقة.
- عدم إرسال القيمة إلى سلة.
- عدم إدراجها في Workflow أو ملفات الموظف أو المورد.

## المعرفات

لا تعتمد على النصوص فقط. احتفظ بالمعرفات الأصلية متى توفرت:

```text

source_item_id
order_item_id
option_id
value_id
custom_field_id
variant_id
sku
```

## أنواع الحقول

ادعم حسب مخطط سلة الفعلي:

- Select / Radio.
- Checkbox أو نعم/لا.
- نص مخصص.
- رقم عند الحاجة.
- الحقول التابعة/الشرطية.

عند تغيير اختيار يغيّر Variant، أعد التحقق من:

- المخزون.
- SKU.
- السعر.
- فرق المبلغ.

## الكمية المتعددة

إذا كانت الكمية أكثر من قطعة ولكل قطعة تخصيص مختلف، يجب إما:

- توفير خيارات مستقلة لكل قطعة، أو
- تقسيمها إلى أسطر منفصلة.

لا تحفظ تخصيصًا واحدًا على كمية متعددة إذا كانت القيم مختلفة.

# 7. فرق المبلغ والدفع

بعد تحديد المنتج والخيارات:

1. احسب السعر من بيانات سلة المؤكدة.
2. احسب فرق المبلغ.
3. إذا كان هناك مبلغ مطلوب، خزّن العملية بحالة:

```text
awaiting_difference_payment
```

4. لا تدخل القطعة في Workflow التجهيز قبل تأكيد الدفع.
5. بعد تأكيد الدفع وFetch الطلب المحدث من سلة، ابدأ تشغيل القطعة.

ممنوع اعتبار الفرق مدفوعًا بدون سجل يتضمن:

- المبلغ.
- العملة.
- وسيلة الدفع.
- المرجع.
- من أكد الدفع.
- الوقت.
- المصدر.

إذا كان الفرق سالبًا، لا تنشئ استردادًا صامتًا. أنشئ Adjustment واضحًا وفق السياسة المالية المعتمدة.

# 9. Workflow القطعة الجديدة

بعد تأكيد سلة والدفع، تبدأ القطعة الجديدة وحدها من:

```text
pending_review
```

ثم تمر بالمراحل الحالية:

```text
انتظار المراجعة
→ تمت المراجعة
→ الإسناد / قيد التنفيذ
→ المورد أو التجهيز الداخلي
→ الاستلام
→ التجميع والعنونة
→ التسليم
```

لا ترجع المنتجات القديمة إلى الخلف.

مثال صحيح:

```text
المنتج 1: التجميع والعنونة
المنتج 2: عند المورد
المنتج 3 الجديد: انتظار المراجعة
```

أنشئ:

- `workflow.items[]` للـ`order_item_id` الجديد.
- `piece_id` لكل وحدة كمية عند materialization.
- Audit events واضحة.

أظهر شارة:

```text
مضاف بعد بدء التجهيز
```

# 10. Reconciliation وCompleteness Gate مركزية

ابنِ خدمة مركزية تقارن أحدث عناصر الطلب وكمياتها من Salla/`unified_orders` مع:

```text
order_review_workflows.items
mezan_preparation_pieces_v1
```

يجب اكتشاف:

- عنصر جديد غير موجود في Workflow.
- كمية زادت ولم تنشأ لها pieces.
- عنصر حُذف تجاريًا وما زال تشغيليًا.
- اختلاف المواصفات أو Variant.
- Workflow أو pieces ناقصة.

## المنع الإلزامي

امنع جميع الانتقالات النهائية إذا كانت المطابقة غير مكتملة، ومنها:

- إنهاء التجميع.
- `ready_to_ship`.
- handoff.
- التسليم للشحن.
- `completed`.

راجع واحمِ تحديدًا:

```text
POST /fulfillment-v2/batches/{batch_id}/handoff
```

لا تجعل الحماية UI فقط. استخدم Policy/Guard مشتركة لكل Endpoints النهائية.

رسالة المنع يجب أن تعرض:

- رقم الطلب.
- المنتج/القطعة الناقصة.
- الكمية المتوقعة والممثلة.
- المرحلة الحالية.
- الإجراء المطلوب.

# 13. أثر التعديل على المورد وملفات التجهيز

## قبل إرسال المورد

- يجب أن تقرأ ملفات الموظف والمورد آخر `specification_version`.
- تظهر القيم الجديدة فورًا في الـsnapshot التالي.

## بعد إنشاء/إرسال ملف المورد

لا تعدل البيانات بصمت.

يجب:

- إنشاء تعليمة على مستوى `order_item`.
- وضع `operational_hold` على القطعة المعنية.
- اعتبار الملف القديم `superseded` أو `invalidated`.
- إنشاء نسخة جديدة برقم إصدار.
- الاحتفاظ بالنسخة القديمة في Audit.
- منع استمرار القطعة حتى تأكيد التعامل مع التعديل.

أعد استخدام النظام الحالي، مثل:

```text
scope = item
target_ids = [order_item_id]
target_stages = [...]
enforcement = completion_required
```

لا تبنِ نظام تنبيهات مكررًا.
