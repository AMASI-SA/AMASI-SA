## قرار الدفاتر الجديدة

- ميزان 2 دفتر جديد يبدأ عند لحظة قطع واحدة معتمدة وذات منطقة زمنية.
- يمنع استيراد أو ترحيل أو إعادة إنشاء أو إعادة ترحيل القيود والحركات
  المالية التاريخية من ميزان القديم.
- تمثل الحالة السابقة للقطع بمجموعة أرصدة افتتاحية واحدة، متوازنة،
  مدعومة بأدلة غير مستخرجة من ميزان القديم.
- بعد القطع، تنشئ الأحداث الموثوقة فقط قيودًا idempotent.
- يمنع دائمًا نسخ التاريخ المالي أو الأرصدة أو القيود أو اعتبار أي قيمة من
  ميزان القديم evidence. لا تدخل هذه البيانات في payload مالي أو journal
  أو opening balance.
- يجوز فقط نسخ تعريف أو إعداد غير مالي إلى مسودة
  `unverified_nonfinancial_draft` تحمل provenance واضحًا. لا تعتمد هذه
  المسودة ولا ترحل شيئًا؛ وبعد مراجعة المالك تصبح إعداد ميزان 2 جديدًا فقط،
  ولا تتحول إلى دليل مالي أو رصيد افتتاحي.

## فصل بوابة البناء عن بوابة التشغيل

يمكن بدء بناء المرحلة التالية بعد تحقق بوابة تنفيذ المرحلة السابقة، حتى لو
بقيت الحالة العامة للمرحلة السابقة `IN_PROGRESS` أو
`RUNTIME_ACCEPTANCE_PENDING`. لا يعد نجاح الكود أو CI أو الدمج قبولًا
تشغيليًا، ولا يجيز Publish أو الكتابة المالية.

لكل مرحلة أربعة محاور مستقلة:

- `implementation_status`: `QUEUED` ثم `IN_PROGRESS` ثم `VERIFIED`
  ثم `MERGED`.
- `release_status`: `UNPUBLISHED` ثم `AWAITING_BATCH_RELEASE` ثم
  `PUBLISHED_VERIFIED`.
- `runtime_acceptance_status`: `NOT_ELIGIBLE` أو `PENDING` أو
  `PARTIAL` أو `PASS`.
- `financial_activation_status`: يبقى `LOCKED` حتى القيد الافتتاحي
  المتحقق و`safe_active=true`.

لا تستخدم `COMPLETE` إلا بعد:

1. دمج التنفيذ المراجع.
2. نشر الحزمة الموحّدة والتحقق منها عبر Release Guard.
3. نجاح قبول Runtime المطلوب.
4. ولأي مسار مالي: إجراء القبول المالي بعد `safe_active=true`.

## ترتيب التنفيذ المعتمد

1. بناء P01 إلى P08 واختبار كل مسار دون Publish أو كتابة Production مالية.
2. تثبيت source commit A النهائي بعد اكتمال المصدر المراجع، وقبل الدمج
   النهائي إلى Production.
3. تنفيذ البناء/التجميد المحكوم من A والتحقق من مخرجاته.
4. إنشاء intent-only commit B ابنه المباشر، بحيث يغير
   `release/release-intent-v5.json` فقط ويشير إلى A.
5. تشغيل CI ومراجعة A/B، ثم دمجهما مع الحفاظ على commit A وcommit B دون
   squash أو rebase، ودفعهما لتشغيل Release Readiness.
6. التوقف عند مرشح مدمج محفوظ الهوية ينتظر موافقة Publish؛ لا تنفذ
   `prepare` أو `prepublish` قبلها.
7. بعد موافقة Publish الصريحة للهوية نفسها، نفذ `prepare` ثم
   `prepublish` وPublish واحدًا للحزمة كاملة وهي خاملة ماليًا.
8. التحقق عبر Release Guard وتنفيذ اختبارات Production غير المالية فقط.
9. إدخال أدلة القطع الثمانية وحفظها كمسودات، ثم إنشاء معاينة افتتاحية
   متوازنة.
10. بعد تفويض مالي صريح مستقل، ترحيل مجموعة القيد الافتتاحي الوحيدة والتحقق
    منها.
11. اشتقاق `safe_active=true` فقط بعد نجاح التحقق؛ لا يضبط يدويًا لتجاوز
    النقص.
12. تنفيذ السيناريو 6 المنقول من P01 وبقية قبول P08 بعد تفويضها، ثم فترة
    الاستقرار.
13. تحديث الحالات إلى `COMPLETE` فقط بعد أدلة Runtime النهائية.

الـPublish الواحد هو خطة الإصدار المعتمدة، وليس إذنًا لمحاولة ثانية عند
الفشل. أي إعادة نشر أو إصلاح لاحق يحتاج دورة Release Guard وتفويضًا منفصلًا.

## نشر خامل وفشل مغلق

بعد Publish وقبل `safe_active` يجب أن ترفض جميع مسارات كتابة القيود
العادية قبل أي تغيير مسودة أو ledger أو audit. الاستثناء الوحيد هو مسار
القيد الافتتاحي المحكوم بعد اكتمال الأدلة والمعاينة والموافقة الصريحة. مجرد
إخفاء أزرار Frontend لا يحقق هذا الشرط؛ Backend هو الحاجز الملزم.

## بوابات السلامة التي تمنع تثبيت A

لا يثبت source commit A قبل إغلاق هذه البوابات باختبارات تنفيذية:

1. دفتر MZ2 منفصل ماديًا:
   `accounting_journal_groups_v2` و`accounting_general_ledger_v2` و
   `accounting_audit_log_v2` وsequences V2، مع `operation_id` إلزامي.
   `general_ledger` Legacy archive فقط؛ لا union/migration/backfill/
   fallback، وgeneric `/ledger` ليس واجهة MZ2.
2. كل مسارات Legacy/import/backfill/replay/admin/bulk/manual وأي endpoint
   بديل للكتابة تفشل قبل mutation عندما `safe_active=false`؛ الاستثناء
   الوحيد هو endpoint القيد الافتتاحي المحكوم.
3. إنشاء مجموعة القيد ورأسها وأرجلها وحالة idempotency يتم داخل transaction
   واحدة all-or-nothing؛ أي خطأ يترك صفر مجموعة جزئية وصفر أرجل جزئية.
4. كل قراءة مالية مقيدة بالـtenant وبـcutover operation نفسها، وتقرأ مجموعة
   الافتتاح المتحققة والقيود اللاحقة فقط. يمنع `current_balance` وأي
   summary أو Ledger قديم كمصدر للأرصدة.
5. حدث الطلب ينشئ مجموعة مكتملة واحدة تشمل، حسب انطباقها، البيع وVAT
   والذمة/النقد والشحن/الرسوم وCOGS والمخزون. نقص تكلفة أو حساب أو رجل
   يحول العملية إلى `needs_review` ويفشل قبل أي قيد جزئي.
