# بروتوكول إدخال بيانات المحاسبة عبر المتصفح السحابي

هذا الملف مخصص لأي محادثة ChatGPT تستلم من المالك مهمة إدخال بيانات في
ميزان عبر المتصفح. بوابة **بناء** مرحلة لاحقة تعتمد
`implementation_status` للمرحلة السابقة ولا تنتظر `COMPLETE` أو Publish.
أما كتابة/اختبار Production عبر المتصفح فتتبع
`runtime_acceptance_status` وبوابة التشغيل أدناه.

## قبل فتح المتصفح

1. اقرأ `STATUS.json` وحدد `current_implementation_phase` ومحاور
   implementation/release/runtime/financial activation، ولا تستنتج أحدها
   من الآخر.
2. اقرأ ملف المرحلة المقصودة وبوابتي التنفيذ وRuntime.
3. يجوز بناء المرحلة التالية بعد
   `previous.implementation_status=VERIFIED` دون Publish ودون
   `previous.status=COMPLETE`. لا تدخل بيانات Production لمجرد أن البناء
   مسموح.
4. افحص صلاحية المستخدم المطلوبة. الإدخال العادي يحفظ مسودة؛ الترحيل والاعتماد يحتاجان تفويضًا صريحًا وصلاحية مستقلة.
5. لا تبدأ إدخال Production قبل نشر الحزمة الواحدة خاملًا والتحقق من SHA
   عبر Release Guard. لا تبدأ كتابة مالية عادية قبل `safe_active=true`.
   endpoint الافتتاح هو الاستثناء الوحيد، ويتطلب بوابته وتفويضًا ماليًا
   مستقلًا.
6. تحقق أن الشاشة تستخدم واجهات دفتر V2 المقيدة بـ`operation_id`؛
   generic `/ledger` و`general_ledger` Legacy archive وليسا مصدرًا
   لبيانات MZ2.

## صيغة السؤال للمالك

اطلب الحقول الناقصة فقط، في رسالة واحدة مرتبة. لا تطلب بيانات موجودة بالفعل في الشاشة أو المستند المرفوع. استخدم الأرقام الإنجليزية في الحقول المالية.

مثال:

> أحتاج لإكمال سجل سمسا: تكلفة الشحنة قبل الضريبة، هل السداد مقدم أو آجل، ضريبة الخدمة، شرائح COD وحدود كل شريحة، الرسم الثابت، ضريبة العمولة، والبنك الحالي للتسوية. أرسل القيم فقط، وسأعرض المعاينة قبل الحفظ.

## تصنيف المصدر لكل قيمة

كل حقل يدخل يجب أن يحمل مصدرًا واضحًا حيث تدعم الواجهة ذلك، أو يوثق في سجل الجلسة:

| المصدر | الحالة | هل يسمح بالترحيل؟ |
|---|---|---|
| `provider_statement` | متحقق من كشف مزود | فقط بعد المطابقة وبوابة التشغيل والتفويض المالي |
| `provider_invoice` | متحقق من فاتورة | فقط بعد بوابة التشغيل والتفويض ضمن الفترة المغطاة |
| `bank_statement` | متحقق بنكيًا | فقط بعد بوابة التشغيل والتفويض ضمن القطع/التسوية |
| `owner_confirmed` | أكده المالك يدويًا | إعداد تشغيلي؛ لا يثبت رصيدًا افتتاحيًا وحده |
| `legacy_copy` | تعريف/إعداد غير مالي فقط، مع provenance | لا؛ مسودة غير معتمدة ولا تصلح evidence أو رصيدًا |
| `system_observed` | رصده النظام من سلة/الطلبات | للمطابقة؛ لا يتغلب على المستند الرسمي |

يمنع دائمًا نسخ التاريخ المالي أو الأرصدة أو القيود أو evidence من ميزان
القديم، حتى مع تأكيد المالك. تعريف/إعداد غير مالي فقط يمكن أن يبقى
`unverified_nonfinancial_draft` مع provenance؛ بعد مراجعة المالك يصبح
إعداد ميزان 2 جديدًا، ولا يتحول إلى دليل مالي أو رصيد افتتاحي. لا يعود
النظام إلى ميزان القديم Runtime.

## خطوات التنفيذ في المتصفح

1. افتح الصفحة من داخل قسم `المحاسبة` كلما كانت الصفحة الموحدة متاحة.
2. اقرأ القيم الموجودة ولا تفترض أن الصفر يعني «لا يوجد»؛ قد يعني «غير مُدخل».
3. قارن البيانات بالمستند أو برسالة المالك.
4. أدخل الحقول واحفظ **مسودة** أولًا فقط عندما تكون بوابة Runtime للمسار
   مفتوحة. قبل `safe_active` يسمح فقط بمسودات أدلة P07 بعد النشر الخامل
   المتحقق؛ لا تحفظ مسودة حركة مالية عادية.
5. اعرض للمالك ملخص المعاينة: المصدر، الإجمالي، العمولة، الضريبة، الصافي، البنك، والفترة.
6. لا تضغط ترحيل/اعتماد/تفعيل إلا بعد موافقة صريحة في نفس المحادثة.
7. بعد الحفظ أعد فتح السجل وتأكد أن القيم استمرت ولم تُحذف أو تتحول وحداتها.
8. اختبر الحدود الحسابية المهمة، خصوصًا شرائح COD عند `1,000` و`3,000` ونحوها.
9. سجل نتيجة الجلسة في ملف المرحلة: ما أُدخل، ما بقي، وأي خطأ واجهة أو API،
   وحدد هل الدليل implementation أم Runtime.
10. حدّث `STATUS.json` عبر PR إذا تغير محور فعلي؛ لا تجعل
    `implementation_status=VERIFIED/MERGED` دليلًا على Runtime أو
    `COMPLETE`.

## بيانات يمنع وضعها في GitHub

- كلمات المرور.
- رموز OTP وMFA.
- مفاتيح API والتوكنات.
- رقم بطاقة أو حساب كامل.
- كشف بنكي كامل أو معلومات عميل حساسة.

يوثق GitHub اسم البنك ومرجع المستند وآخر أربع خانات عند الحاجة فقط. الملف الأصلي يرفع إلى مساحة الأدلة داخل التطبيق أو مخزن الملفات المصرح.

## قوالب طلب البيانات حسب المرحلة

### P01 — التسويات

لكل مزود:

- اسم المزود: سلة / تمارا / تابي / إمكان / شركة شحن.
- البنك الحالي لاستقبال التسوية.
- مرجع الحساب أو آخر أربع خانات.
- فترة الكشف.
- رقم/مرجع الكشف.
- الإجمالي قبل الخصومات.
- العمولة قبل الضريبة.
- ضريبة العمولة.
- الاستردادات والإلغاءات والتعديلات.
- صافي التحويل.
- تاريخ وصول البنك.
- المستند الداعم.

### P02 — شركة شحن خارجية

- اسم الشركة.
- نشطة أو متوقفة.
- تكلفة الشحنة قبل الضريبة.
- ضريبة خدمة الشحن.
- دفع مقدم أو آجل.
- البنك الحالي للتسوية.
- شرائح COD: بداية ونهاية وشمول الحدود والنسبة والرسم الثابت وضريبة العمولة.
- تاريخ سريان الإعداد.
- مصدر القيمة: عقد/فاتورة/كشف/تأكيد المالك/نسخ قديم.

### P02 — مندوب متجر

- الموصل الموجود في إدارة الموصلين؛ لا ينشأ شخص مكرر.
- `driver_id` أو السجل المختار.
- سعر التوصيلة.
- تاريخ سريان السعر.
- هل السعر شامل الضريبة أو غير خاضع، حسب الاتفاق الفعلي.
- حالة الموصل.
- أي رصيد COD افتتاحي يؤجل إلى P07 ولا يدخل هنا.

### P03 — فاتورة شراء

- المورد.
- رقم وتاريخ الفاتورة.
- المنتجات والكميات.
- سعر الوحدة والخصم والضريبة.
- المدفوع والمتبقي.
- حساب الدفع.
- تاريخ الاستلام.
- المستند الداعم.

### P04 — حركة مالية

- نوع العملية الفعلية.
- الطرف المقابل.
- المبلغ والتاريخ.
- الحساب البنكي/النقدي.
- المرجع والوصف.
- المرفق.

لا يُطلب من المستخدم العادي اختيار المدين والدائن.

### P05 — راتب أو التزام

- الموظف أو الجهة.
- نوع الاستحقاق.
- الفترة.
- المبلغ الإجمالي.
- السلف والخصومات.
- صافي المستحق.
- تاريخ الاستحقاق والسداد.
- حساب السداد.
- العقد/الكشف/الفاتورة.

### P07 — القطع والأرصدة الافتتاحية

لا يدخل شيء قبل تحديد توقيت قطع واحد. لكل بند يلزم رصيد **عند نفس
اللحظة** ومستند مطابق لها. عند `11/13` فقط يمكن اعتماد المعاينة بتفويض
صريح؛ الاعتماد يسجل البند 12 دون قيد. عند `12/13` فقط يمكن ترحيل
المعاينة المعتمدة بتفويضها. نجاح الترحيل والتحقق يحقق البند 13 و
`13/13`، ثم فقط تشتق `safe_active=true`.

## نتيجة الجلسة الإلزامية

يجب أن تنتهي كل جلسة بإحدى الحالات:

- `DRAFT_SAVED_AND_REOPEN_VERIFIED`
- `DATA_MISSING_NO_WRITE`
- `VALIDATION_FAILED_NO_POST`
- `APPROVED_12_OF_13_NO_POST`
- `POST_FAILED_REMAINS_12_OF_13_SAFE_INACTIVE`
- `POSTED_AND_VERIFIED_13_OF_13_WITH_EXPLICIT_AUTHORIZATION`
- `BLOCKED_BY_PHASE_GATE`

ولا يجوز إنهاء الجلسة بعبارة عامة مثل «تم» دون تحديد السجلات والحالة الفعلية.
