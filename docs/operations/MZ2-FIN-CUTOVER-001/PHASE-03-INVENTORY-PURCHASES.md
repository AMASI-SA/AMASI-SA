# P03 — المخزون والمشتريات

الحالة: **QUEUED — IMPLEMENTATION_NOT_STARTED / RUNTIME_NOT_ELIGIBLE**

بوابة البناء: **بعد `P02.implementation_status=VERIFIED`**

بوابة Runtime: **ضمن P08 بعد النشر الخامل المتحقق والقيد الافتتاحي و`safe_active=true`**

## الهدف

تنفيذ صفحة موحدة للمخزون والمشتريات تسمح للمستخدم بتسجيل فاتورة الشراء والاستلام الفعلي فقط، بينما ينشئ النظام المخزون وضريبة المدخلات وذمة المورد أو حركة البنك والقيد المتوازن تلقائيًا.

نجاح بوابة تنفيذ P03 يفتح **بناء** P04 دون Publish ودون انتظار
`P02/P03 COMPLETE`. القبول التشغيلي يبقى منفصلًا إلى P08.

## النطاق

- الموردون الفعليون.
- فواتير الشراء.
- استلام المخزون كاملًا أو جزئيًا.
- ربط بنود الفاتورة بمنتجات وخيارات ميزان 2.
- تكلفة الوحدة وتحديث تكلفة المخزون.
- المدفوع والمتبقي وذمة المورد.
- سداد المورد من حساب فعلي.
- المرفقات والمراجعة والترحيل.

## سياسة المصدر القديم

يسمح فقط بنسخ اسم المورد وبياناته التعريفية غير المالية كمسودة
`unverified_nonfinancial_draft` تحمل provenance. يراجعها المالك لتصبح
تعريف ميزان 2 جديدًا؛ لا تصبح evidence ولا تنشئ رصيدًا أو قيدًا. يمنع
دائمًا نسخ:

- رصيد المورد القديم.
- قيمة مخزون قديمة.
- كميات غير مثبتة بجرد أو استلام.
- فواتير غير متحقق منها.
- تكلفة افتتاحية مشتقة من مركز ميزان القديم.

الرصيد الافتتاحي للمورد والمخزون يعالج في P07 من أدلة القطع فقط.

## تصميم الصفحة

### التبويب 1 — فاتورة شراء جديدة

يدخل المستخدم:

- المورد.
- رقم الفاتورة وتاريخها.
- العملة `SAR` في المرحلة الحالية.
- المنتجات أو المكونات والكميات.
- سعر الوحدة قبل الضريبة.
- الخصم.
- نسبة وقيمة الضريبة.
- إجمالي الفاتورة.
- المدفوع الآن.
- حساب الدفع إن وجد.
- تاريخ الاستحقاق للمتبقي.
- المرفق.

النظام يعرض معاينة ولا يطلب المدين والدائن.

### التبويب 2 — الاستلام

- اختيار الفاتورة.
- تسجيل الكمية المستلمة لكل بند.
- دعم الاستلام الجزئي.
- منع استلام كمية أكبر من المتبقي دون إجراء تصحيح مصرح.
- ربط المستلم والمستودع والتاريخ والمرفق عند الحاجة.
- عدم رفع قيمة المخزون قبل حدث الاستلام وفق السياسة المعتمدة.

### التبويب 3 — الموردون والذمم

لكل مورد:

- فواتير مفتوحة.
- إجمالي مستحق.
- إجمالي مدفوع.
- المتبقي.
- الدفعات.
- المرفقات.
- كشف حساب من القيود.

## القيد المحاسبي

حسب حالة الفاتورة والاستلام والدفع، يجب حفظ الأرجل منفصلة، ومنها:

- مخزون أو مشتريات مستلمة.
- ضريبة مدخلات.
- ذمة المورد.
- بنك/صندوق للمدفوع.
- خصم أو تعديل مثبت.

لا يجوز إنشاء قيدين لنفس الفاتورة أو الاستلام عند إعادة الطلب. كل حدث يملك idempotency key واضحًا.

## تكلفة المخزون

- تعتمد الكمية المستلمة فعليًا.
- تحفظ تكلفة الوحدة الموثقة على بند الاستلام.
- تحديث التكلفة يتم وفق سياسة تكلفة واحدة موثقة، والهدف المعتمد هو المتوسط المرجح عند وجود مشتريات متعددة.
- التعديل اللاحق لا يعيد كتابة قيود أو تكاليف تاريخية مرحلة؛ يصحح بمستند تعديل أو قيد عكسي وفق P06.
- تكلفة المخزون الافتتاحية لا تستنتج من المبيعات أو ميزان القديم؛ تؤخذ من الجرد المعتمد في P07.

## البيانات التي يطلبها وكيل المتصفح

لكل فاتورة:

1. المورد.
2. رقم وتاريخ الفاتورة.
3. صورة أو ملف الفاتورة.
4. البنود والكميات والأسعار.
5. الخصم والضريبة.
6. المدفوع والمتبقي.
7. حساب الدفع.
8. تاريخ الاستحقاق.
9. الكميات المستلمة وتاريخ الاستلام.

عند توفر الملف، يستخرج النظام البيانات ويطلب فقط الحقول غير الواضحة أو المطابقة الناقصة للمنتج.

## متطلبات Backend

- فهرس فريد للمورد ورقم الفاتورة داخل tenant.
- حالات: `draft`, `reviewed`, `partially_received`, `received`, `posted`, `reversed`, `needs_review`.
- منع التكرار عند رفع نفس الفاتورة أو تسجيل نفس الاستلام.
- snapshot للسعر والضريبة والخصم على كل بند.
- ربط الفاتورة والاستلام والدفع بمجموعات القيود.
- حساب ذمة المورد من `accounting_general_ledger_v2` المقيد بالعملية، لا
  من `current_balance` أو حقل رصيد قابل للتعديل.
- رأس مجموعة الشراء/الاستلام/الدفع وأرجلها وحالة idempotency والترحيل
  transaction واحدة all-or-nothing؛ الفشل لا يترك مجموعة أو أرجلًا جزئية.
- كل قراءة مخزون أو ذمة تقيد بالـtenant وبـcutover operation، ولا تعمل
  union مع `general_ledger` المصنف Legacy archive.
- حاجز `safe_active` يغطي Legacy/import/backfill/replay/admin/bulk/manual
  وأي endpoint بديل قبل mutation.
- عقد تكلفة موحد يزوّد قيد الطلب بتكلفة موثقة؛ غياب تكلفة أو mapping يجعل
  حدث الطلب `needs_review` ويمنع قيد بيع/COGS جزئيًا.
- صلاحية `accounting.purchases.post` للترحيل.
- سجل تدقيق لكل تعديل قبل الترحيل.

## متطلبات Frontend

- نموذج واحد مبسط مع إجراء رئيسي حسب الحالة.
- بحث المنتج/الخيار مع منع الربط الغامض.
- عرض الإجمالي والضريبة والمدفوع والمتبقي بالإنجليزية.
- حفظ مسودة للمستخدم العادي.
- مراجعة وترحيل للمحاسب فقط.
- شاشة استلام سهلة تدعم الجزئي.
- كشف حساب مورد قابل للفتح والطباعة.

## الاختبارات الإلزامية

- فاتورة مكررة تُمنع.
- الاستلام الجزئي لا يعتبر الفاتورة مكتملة.
- الاستلام الزائد يُمنع.
- المدفوع الجزئي ينشئ ذمة صحيحة.
- ضريبة المدخلات منفصلة.
- إعادة الإرسال لا تكرر القيد.
- فشل رجل وسطية لا يترك رأسًا أو أرجلًا جزئية، وإعادة المحاولة تنشئ
  المجموعة مرة واحدة.
- المتوسط المرجح يحسب من الكميات والتكاليف المستلمة.
- تعديل فاتورة مرحلة غير مسموح؛ التصحيح عبر عكس/مستند تصحيح.
- مستخدم بلا صلاحية ترحيل يفشل من الواجهة والـAPI.
- bypasses القديمة والبديلة ترفض قبل mutation عند
  `safe_active=false`.
- قراءات المخزون والذمم operation-scoped ولا تعتمد على
  `current_balance` أو `general_ledger`.
- تكلفة مفقودة تمنع مجموعة الطلب كلها وتظهر `needs_review`.

## سيناريوهات اختبار المتصفح

1. إضافة مورد جديد كبيانات تعريفية فقط.
2. رفع فاتورة وملء البنود وحفظ مسودة.
3. دفع جزئي واستلام جزئي ثم إعادة فتح السجل.
4. إكمال الاستلام والتحقق من المخزون والذمة.
5. محاولة رفع نفس الفاتورة مرتين.
6. فتح كشف المورد والقيد والمرفق.
