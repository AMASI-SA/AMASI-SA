# P08 — التفعيل والتحقق بعد القطع

الحالة: **QUEUED — IMPLEMENTATION_NOT_STARTED / RUNTIME_NOT_ELIGIBLE**

بوابة البناء: **ضمن الحزمة غير المنشورة بعد بوابة تنفيذ P07**

بوابة Runtime: **LOCKED_UNTIL_PUBLISHED_VERIFIED_OPENING_VERIFIED_AND_SAFE_ACTIVE**

## الهدف

بناء اختبارات ومراقبة التفعيل ضمن المصدر غير المنشور، ثم إثبات بعد القطع
أن ميزان 2 يعمل كنظام محاسبي مستقل: كل حدث تشغيلي جديد ينتج قيدًا واحدًا
متوازنًا وقابلًا للتدقيق، ولا توجد قراءة مالية أو كتابة من ميزان القديم.
نجاح بناء P08 لا يجيز تشغيل اختبار مالي.

## شروط البدء

- الحزمة الموحّدة منشورة وهي خاملة ومتحقق منها عبر Release Guard.
- P07 `COMPLETE`.
- `13/13` جاهزية.
- قيد افتتاحي مرحل ومتحقق.
- `safe_active=true` للعملية نفسها.
- Production SHA معروف ومتحقق عبر release guard.
- لا يوجد import أو migration أو recreation أو backfill مالي تاريخي.
- يوجد تفويض مالي صريح مستقل لكل اختبار حقيقي يحتاجه القبول.

موافقة Publish لا تحقق الشرط الأخير.

## السيناريو 6 المنقول من P01

أول اختبار مالي بعد التفعيل هو السيناريو 6:

1. استخدام تسوية مصرح بها تخص حدثًا بعد القطع، أو تحصيلًا بعد القطع لذمة
   افتتاحية مثبتة.
2. إذا عبر الكشف لحظة القطع، يفصل الجزء السابق ويعامل كتسوية للذمة
   الافتتاحية فقط؛ لا يعاد تسجيل مبيعاته أو رسومه التاريخية.
3. ترحيل مجموعة واحدة وفتح القيد والمرفق.
4. إعادة الطلب بالمفتاح نفسه والتحقق من عدم إنشاء مجموعة ثانية.
5. توثيق أن العملية لم تقرأ Legacy ولم تنشئ أثرًا سابقًا للقطع.

لا ينفذ هذا السيناريو إلا بعد الشروط أعلاه والتفويض المالي الصريح في
الجلسة نفسها.

## نطاق التحقق

يختبر حدثًا فعليًا أو تجريبيًا مصرحًا لكل مسار:

- طلب/بيع وتسوية سلة.
- تسوية تمارا.
- تسوية تابي.
- تسوية إمكان.
- شحنة خارجية وتحصيل COD.
- توصيل مندوب متجر COD.
- توصيل مندوب متجر prepaid.
- فاتورة شراء واستلام مخزون.
- سداد مورد.
- حركة مالية عامة صحيحة.
- استحقاق راتب وسداد.
- التزام دوري وسداد.
- عكس قيد مصرح.

## قاعدة القيد الواحد

لكل event id أو statement id أو invoice id أو assignment/delivery id:

- مجموعة قيد واحدة فقط.
- idempotency key ثابت.
- إعادة webhook أو الطلب لا تكرر المجموعة.
- كل الأرجل تحمل المصدر والمرجع والمستخدم والوقت.
- المدين يساوي الدائن.
- المستند أو الحدث قابل للفتح من القيد والعكس.

## التحقق من الاستقلال عن ميزان القديم

يجب إثبات:

- لا endpoint مالي يقرأ رصيدًا أو مبيعات أو تكلفة أو ذمة من قاعدة/مجموعة Legacy.
- القيم المنسوخة سابقًا أصبحت إعدادات مستقلة في ميزان 2.
- تعطيل الوصول إلى ميزان القديم لا يغير القيود أو التقارير الجديدة.
- لا عملية backfill تلقائية تعمل بعد التفعيل.
- أي حقل provenance قديم يبقى للتدقيق ولا يستخدم كمصدر مالي معتمد.

## المطابقة اليومية الأولى

لمدة تشغيل أولية معتمدة، يراجع النظام:

- عدد الأحداث مقابل عدد مجموعات القيود.
- المجموعات غير المتوازنة.
- التكرارات.
- المستندات بلا قيد والقيود بلا مستند.
- التسويات مقابل البنك.
- COD مقابل الشركات والموصلين.
- المخزون مقابل الاستلام والصرف.
- ذمم الموردين والموظفين.
- الحسابات غير المصنفة.

أي فرق يفتح مهمة `needs_review` ولا يصحح بصمت.

## بروتوكول النشر

النشر الأول المخطط لهذه العملية يحدث قبل التنفيذ التشغيلي لـP07، ويشمل
كل مصدر P01–P08 في حزمة واحدة خاملة. لا يعاد Publish داخل P08 لمجرد بدء
القبول. أي تغيير Runtime أو إصلاح جديد بعد ذلك يستخدم من `/app`:

كل تغيير Runtime في P08 أو إصلاح بعد القطع يستخدم من `/app`:

1. فحص `python scripts/production_release_guard.py status` وعدم المتابعة حتى تكون `active: false`.
2. تحديث workspace إلى `origin/hotfix/prod-snap-meta-final` دون reset قسري.
3. قبل إنشاء أي lease، تنفيذ bootstrap والتثبيت المجمد والبناء المحكوم والتحقق:

   ```bash
   python scripts/frontend_release_toolchain.py ensure

   python scripts/frontend_release_toolchain.py exec -- \
     bash -lc 'cd frontend && yarn install --frozen-lockfile --non-interactive'

   python scripts/frontend_release_toolchain.py exec -- \
     bash -lc 'cd frontend && yarn build:release'

   python scripts/frontend_release_toolchain.py exec -- \
     python scripts/verify_frontend_build.py \
       --expected-git-sha "$(git rev-parse HEAD)"
   ```

4. بعد نجاح الخطوات السابقة فقط، تنفيذ `python scripts/production_release_guard.py prepare --actor "<actor>"`.
5. تنفيذ `python scripts/production_release_guard.py prepublish` مباشرة قبل إعادة النشر.
6. Publish مرة واحدة ضمن التفويض المحدد.
7. انتظار `Deployment Succeeded` أحدث.
8. تنفيذ `python scripts/production_release_guard.py verify --url https://mezansalla.com`.
9. عدم تنفيذ كتابة مالية حتى `verified: true` للـSHA نفسه و`active: false`.

## معالجة الخطأ بعد القطع

- لا تعدل القيد التاريخي.
- أوقف المسار المتأثر إذا كان يولد تكرارًا أو عدم توازن.
- سجل المهمة والدليل.
- اعكس القيد الخاطئ عند الحاجة بصلاحية صريحة.
- أصلح الكود واختبره وانشره عبر الحارس.
- أعد تشغيل الحدث فقط بمفتاح idempotency يمنع الازدواج.

لا يجرى rollback لقاعدة البيانات بإزالة القيود المرحلة يدويًا.

## لوحة مراقبة ما بعد القطع

تعرض على الأقل:

- Production SHA وحالة التحقق.
- cutover at وoperation id.
- آخر قيد ناجح لكل مسار.
- أحداث بلا قيد.
- قيود مكررة أو غير متوازنة.
- مستندات تحتاج مراجعة.
- فروق البنوك والمزودين وCOD.
- عدد الحسابات غير المصنفة.

## الاختبارات الإلزامية

- إعادة كل webhook أو request لا تكرر القيد.
- كل المسارات تنتج مجموعة متوازنة.
- جميع كتاب القيود العادية يرفضون قبل أي mutation عندما تكون
  `safe_active=false`.
- التقارير تتغير بنفس أثر القيود فقط.
- إيقاف Legacy لا يغير النتائج.
- مستخدم غير مخول لا يرحل أو يعكس.
- فشل النشر أو اختلاف SHA يمنع الكتابات الحساسة.
- لا ينشئ كشف عابر للقطع مبيعات أو رسومًا تاريخية مرة ثانية.
- العكس يعمل دون حذف الأصل.
- مراقبة الاستثناءات تلتقط الحدث المفقود والمكرر.

## سيناريوهات اختبار المتصفح

1. تنفيذ السيناريو 6 المنقول من P01 وفتح القيد والمرفق.
2. فتح الرئيسية والتحقق من الأرصدة بعد القطع.
3. تنفيذ أو مراجعة سجل من كل مسار ضمن قائمة النطاق.
4. فتح القيد والمرفق من العملية.
5. تكرار الطلب/التحديث والتحقق من عدم الازدواج.
6. مقارنة تقرير البنك والمزود وCOD بالمستند.
7. اختبار حساب موظف بصلاحيات محدودة.
8. فتح لوحة المراقبة والتأكد من عدم وجود مانع.

## فترة الاستقرار

لا تغلق العملية فور أول نجاح. يجب تسجيل فترة استقرار متفق عليها في `STATUS.json` تتضمن:

- تاريخ البداية والنهاية.
- عدد الأحداث المختبرة.
- عدد الاستثناءات.
- الاستثناءات المغلقة والمفتوحة.
- آخر Production SHA متحقق.

المدة تحدد عند بدء P08 حسب حجم التشغيل، ولا تُفترض مسبقًا.
