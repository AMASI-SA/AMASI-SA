# تصميم مقترح للمراجعة، غير منفذ

هذا التصميم لميزان 2 وحده. لا تنشأ شاشة أو عملية جديدة في القديم، ولا قراءة مالية منه، ولا fallback عند نقص دليل ميزان 2. استعمال ملف مشترك أو دالة نقية لا يعني جواز استعمال مجموعات القديم. يستمر العمل عند تعطيل القديم؛ ما لا تتوافر له بيانات MZ2 معتمدة يذهب إلى `needs_review`، لا إلى مصدر قديم بديل.

## الهوية ودورة الشحنة

أبعاد كل دليل/حركة: `owner_id` الذي يحسمه الخادم، `operation_id=MZ2-FIN-CUTOVER-001`، العملة، هوية الطرف، `shipment_key`، `event_key`، تاريخ الحدث الأصلي، `accounting_at`، ونسخة الدليل. هذه أسماء عقد مقترح، لا schema مطبق.

- الشركة الخارجية: هوية MZ2 ثابتة مع alias لـ`shipping:{courier_key}` المملوك لربط البنك؛ لا خلط `counterparties.id` القديم بالـcourier_key. أي تعارض/تعدد في alias يمنع الترحيل حتى الربط الصريح.
- المندوب: `store_drivers.id` عندما يعتمد مسار Amasi Delivery. `users.id` هو حساب دخول وليس شخصًا ماليًا جديدًا. للمسار الآخر store-courier-dispatch يلزم mapping تشغيلي مثبت داخل المالك؛ لا تطابق بالاسم/الهاتف ولا counterparty جديد. «مندوب المتجر» تجميع عرض فقط بلا balance أو allocation.
- الشحنة الخارجية: provider namespace + provider shipment ID؛ تحفظ waybill كمرجع لا هوية وحيدة. المحلية: assignment ID وshipment/attempt ID المعتمد تشغيليًا. رقم الطلب رابط أبوي، وليس مفتاح منع تكرار ولا وعاء COD يتكرر لكل شحنة.
- outbound وreturn وreplacement/reship كيانات/دورات متميزة تربط `parent_shipment_key` وسبب العملية. إعادة تسليم webhook لنفس النجاح لا تنشئ محاولة جديدة. إعادة إسناد نفس الشحنة لا تمنح مندوبين استحقاقًا كاملًا إلا بدليل سياسة استحقاق مختلفة.
- أحداث مستقلة: assigned، picked_up، delivered، cash_collected، fee_earned، returned، statement_line_confirmed، bank_received، fee_paid، explicit_offset. assignment/pickup لا يرحلان مالًا. delivery يثبت الأجرة وفق القاعدة؛ collection يثبت العهدة فقط عند دليل تحصيل، ولا يُستنتج قبض النقد من اسم COD وحده.
- إذا كانت شحنتان لطلب واحد: توزيع المبلغ القابل للتحصيل مثبت بإجمالي لا يتجاوز متبقي الطلب؛ لا تكرار total_amount على كل شحنة. إعادة الشحن لا تعيد البيع/الضريبة تلقائيًا. مردود البضاعة لا يسقط تلقائيًا عهدة نقد ثبت قبضها أو أجرة سبق استحقاقها؛ دليل مستقل لكل عكس.

## الأسعار والضريبة والإعداد المستقل

نسخة سعر MZ2 غير قابلة لإعادة كتابة التاريخ تشمل الطرف، currency، basis (قبل/شامل الضريبة)، base، service VAT rate/amount، COD tiers وCOD VAT، rounding policy، trigger، effective_from/to، evidence_ref/hash، source_kind، verification_status، approved_by/at. تخزن العملية rate_version_id وsnapshot الحساب والدليل؛ تغيير السعر لا يعيد حساب الشحنة السابقة.

17.25 لشركة SMSA/iMile و20 للمندوب **أمثلة فحص فقط**. إذا أثبت الدليل أن 17.25 شامل 15% يكون base=15 وVAT=2.25؛ إذا أثبته قبل الضريبة يصبح VAT=2.59 وtotal=19.84 عند التقريب المصطنع نصف لأعلى. لا يختار النظام المعنى دون دليل، ولا يستنتج أهلية ضريبة المدخلات من الرقم. VAT خدمة الشحن منفصلة عن VAT عمولة COD، ولا توريث صامت لأحدهما من الآخر.

شرائح COD: min/max مع inclusive flags، نسبة بوحدة واضحة (`0.01=1%` في الدالة الموجودة)، رسم ثابت معلوم، ضريبة وrounding policy. لا overlap، الفجوة أو fixed component غير المعتمد تعني needs_review. الحساب لكل شحنة قبضت COD وفق العقد، لا على إجمالي الكشف إلا بدليل صريح. اختلاف مثال master (50..1000: 1%+2) عن PHASE-02 (1..1000: 2%) دليل أنهما ليسا إعدادًا جاريًا مؤكدًا.

المندوب: تستحق الأجرة عند نجاح التوصيل المعتمد، وتُلتقط النسخة عند **تأكيد الإسناد**؛ تغيير السعر بين scan وconfirm يحتاج إظهار السعر الجديد قبل التأكيد. لا يعاد احتساب القديم. للشركات الخارجية لا نعمم هذه القاعدة: PHASE-02 الحالية تقول الاستحقاق عند التوصيل، بينما قد يكون العقد عند إصدار البوليصة أو pickup أو يشمل failed/return. **لا تغيير للقاعدة قبل عرض العقد/الفاتورة والاختلاف للمراجعة**. في غياب دليل لا نفترض الاستحقاق المبكر ولا المجانية.

نسخ لاحق مأذون: ملف تعريفي/سعري واحد إلى تخزين MZ2 مستقل، `source_kind=legacy_copy`, `verification_status=unverified` مع وقت الاستخراج ودليل القيمة ومعنى الضريبة. النسخة مسودة لا قيد ولا رصيد ولا ترحيل. اعتماد المالك لاحقًا ينشئ نسخة MZ2 مؤرخة؛ تغيير أو تعطيل القديم بعدها لا يغيرها. ممنوع نقل COD/payable/stock/قيمة مخزون أو journals، وممنوع runtime query إلى settings القديم بعد النسخ. الافتتاحيات خارج هذا التحضير وتعتمد أدلة القطع فقط.

## الفصل المحاسبي

الأسماء التالية أدوار مقترحة تربطها النواة بالحسابات المعتمدة؛ ليست chart-of-accounts جديدًا. `R` عهدة COD مدينة، `P` التزام أجرة/شحن/عمولة دائن. تحفظ الالتزامات مفصلة لكل charge_id حتى لو عرضتها النواة في حساب رقابي واحد.

| الحدث | القيود المقترحة | شروط وعدم تكرار |
|---|---|---|
| اعتراف الطلب | النواة وحدها: مدين الذمة المناسبة، دائن صافي البيع وضريبته | لا يولد الشحن revenue/VAT legs. يلزم recognition_event_key/group من النواة؛ إذا أثبتت النواة R مباشرة فلا قيد عهدة ثانٍ |
| انتقال العهدة بعد بيع سبق اعترافه | Dr R للطرف، Cr ذمة التحصيل الأصلية المحددة من النواة | فقط مقدار محصل فعليًا ورصيد قابل للتخصيص، مرجع القيد الأصلي إلزامي. لا suspense أو revenue لتغطية نقص العقد |
| prepaid أو بطاقة/تحويل لا في عهدة المندوب | لا R على المندوب | لا نستنتج COD من مجرد وجود shipment أو payment_method label |
| استحقاق أجرة المندوب | Dr تكلفة توصيل، Cr P:delivery_fee_payable لنفس driver | snapshot ودليل نجاح، مرة واحدة لكل استحقاق؛ المثال 20 بلا VAT افتراض fixture فقط |
| استحقاق شحن خارجي | Dr تكلفة شحن قبل الضريبة + Dr ضريبة خدمة مؤهلة بحسب الدليل، Cr P:shipping | إن كانت الخدمة مدفوعة مقدمًا أصلًا، تُستهلك ذمة/دفعة مقدمة معتمدة بدل إيجاد دائن جديد؛ لا bank leg عند الاستهلاك |
| عمولة COD | Dr عمولة + Dr ضريبة عمولة مؤهلة، Cr P:cod_fee | حدث استحقاق مستقل ودليل rate version أو كشف، لا default غير معتمد |
| قبض تحويل COD فقط | Dr bank/cash، Cr R | دليل بنك/نقد حقيقي، bank reference مستقل عن statement reference |
| دفع أجرة/فاتورة | Dr P، Cr bank/cash | لا expense ثانٍ. مصروف لم يثبت أصلًا يحتاج حدث accrual مستقل/مجزأ داخل نفس معاملة النواة قبل الإطفاء |
| مقاصة صريحة | Dr P المخصص، Cr R المخصص | نفس المالك والطرف والعملة؛ بموافقة ودليل allocation. لا netting بين مندوبين أو شركتين |
| تسوية صافية | Dr bank للواصل الحقيقي + Dr P للمقاصة، Cr R بإجمالي ما سُوي | تحفظ gross COD وfee offset وnet independently؛ جزئي أو كامل ضمن الرصيد |
| صافي صفر | Dr P، Cr R فقط | كشف يثبت المقاصة؛ لا bank journal ولا bank receipt ولا bank arrival مزعوم |
| كشف يصحح تكلفة سبق تقديرها | فرق فقط إلى expense/tax/payable أو reversal+replacement مع رابط للأصل حسب عقد النواة | لا إعادة إجمالي التكلفة، ولا تعديل snapshot أو قيد posted؛ tax adjustment يتطلب دليلًا وتصنيفًا صحيحًا |

مثال شركة مصطنع: R=115؛ تكلفة15 + VAT2.25، عمولة2 + VAT0.30 ⇒ P=19.55. صافي موثق95.45 يعطي Dr bank95.45 + Dr P19.55 / Cr R115. يصبح R=P=0، والتكاليف17 والضريبة2.55 لا تتكرر. مثال مندوب: R1000 وP20، قبض980+offset20 يعطي صفرًا للطرف، وليس إثبات إيراد980.

ضريبة خدمة غير مثبتة/غير قابلة للاسترداد لا تدخل input VAT تلقائيًا؛ تُراجع السياسة والدليل قبل تحديد expense أو suspended review. أمثلة fixtures مشروطة بأهلية افتراضية صريحة، ولا تقدم اعتمادًا ضريبيًا للإنتاج.

## العرض والمطابقة

لكل طرف وتاريخ محاسبي: «لنا عنده» = إجمالي COD المفتوح، «له علينا» = إجمالي الشحن/الأجرة/العمولة المفتوح، والصافي signed للعرض. لا إسقاط أحد الإجماليين عندما يصبح الصافي صفرًا. الرصيد المعكوس أو الدفعة الزائدة يظل ظاهرًا بتصنيفه/مراجعته، لا max(...,0) يخفي استثناءً. التفاصيل تفصل accrued/settled/remaining ودليل كل حركة، ونقاط الفترة قبل وبعد التسوية.

الكشف يحتفظ `statement_ref`, issuer/account/period/currency, immutable original hash، version وline IDs. البنك يحتفظ `bank_reference`, bank/account, received_at, amount/currency, receipt/transaction ID. لا يحل أحد المرجعين محل الآخر. نفس bytes أو نفس statement identity مع ملف معاد التصدير لا يصبح كشفًا جديدًا؛ تغيير المحتوى لنفس الهوية conflict للمراجعة. كشف مصحح يحتاج سلسلة supersedes لا تفريغ claims.

التسوية الجزئية تخصيص صريح لسطور وأحداث COD وcharge lots. مجموع allocations لا يتجاوز المفتوح؛ نفس الدليل/المبلغ لا يستهلك مرتين ولو جاء بrequest ID جديد. دفعة بنك مجمعة أو كشف متعدد الدفعات يحتاج residual allocation داخل حدود خدمة P01، وليس تعطيل قيد one-to-one الحالي. اختلاف مبلغ/تاريخ/عملة/طرف أو تعدد مرشحين يذهب للمراجعة. مطابقة مبلغ وتاريخ وحدهما لا تمنح auto-link.

## قرارات لم تحسمها الأدلة

1. تعريفات الشركات والأسعار الجارية المعتمدة، معنى17.25، ضريبة كل خدمة، third tier fixed fee، وحدود/فجوات الشرائح والتقريب.
2. هل استحقاق الشركة عند label/pickup/delivery، وكيف تُعامل الإلغاء والمحاولة الفاشلة والإرجاع وإعادة الشحن؟ يبقى مستند P02 دون تغيير إلى أن يثبت الاختلاف.
3. أي مسار مندوبي متجر تشغيلي معتمد، وكيف يربط users/store_drivers، ومن يملك shipment/attempt identity المتعدد؟
4. عقد اعتراف COD والطلبات متعددة الشحنات، والذمة التي يُعاد تصنيفها عند القبض؛ الحالي BNPL ليس دليل كفاية.
5. قرار النواة بشأن العزل الفعلي لمخزن MZ2 ومنع التاريخ القديم في القراءات. لا دفتر بديل في هذه المهمة.
6. صلاحية وموافقة المقاصة، ودليل الاستلام النقدي، ومعالجة رصيد/تحويل سالب أو زيادة وتخصيص دفعات متعددة؛ لا تعديل لحراس P01 دون تنسيق.
7. تاريخ القطع وافتتاحيات الطرف/البنك والضريبة: خارج المهمة، لا تُستنتج من القديم.
