# One-shot reservation initiation amendment (proposal; runtime off)

The current reservation helper rejects an existing RUNS journal, but an unknown commit which actually did not apply leaves no journal. A restart must not interpret that absence as permission to attempt the reservation again. Deterministic transaction IDs alone do not establish that permission.

The reservation entrypoint will require a private, same-process, same-DB, exact owner/account/grant/permanent-slot/proposal/execution-claim initiation ACK. It is burned synchronously before the first await. Only a future separately acknowledged durable launch-intent preparation may mint it. No producer, activation route, gateway or worker is introduced in this slice. Tests may seed an explicitly future-produced preparation and use the private fixture construction; this is not application authority.

The durable slot key remains user/account/request_key, independent of grant revision. The proposed preparation transaction consumes that slot permanently, sets grant.consumed=true with its exact claim, writes RUNS phase=prepared with immutable grant/review/intent/proposal/fence binding and preparation operation identity, and advances the common account epoch. It does not reserve money, send Google requests or mint funded dispatch permission. Its ACK alone can mint the in-process initiation continuation. Preparation expiration/cancellation/unknown ACK cannot free or reuse the permanent slot.

Reservation changes RUNS prepared→reserved and adds the common budget allocation in one mandatory transaction, validating the exact prepared journal/claim and all current grant/owner/policy/product/native bindings. It must accept an already consumed grant only when that consumption belongs to the exact prepared journal and claim. It never inserts a replacement journal after finding absence. Positive reservation ACK mints the already defined private floor continuation; unknown reservation leaves the initiation continuation burned, whether RUNS remains prepared or becomes reserved. Readback and a new process cannot manufacture either continuation. Configured grants still cannot become active here.

Floor remains reserved→submitted with an acknowledged atomic marker; settlement is submitted/reserved→settled only with its existing positive original outcome proof. Unknown commit/send retains allocation and fence. A prepared-only slot has no money allocation to release but remains permanently consumed; it is not evidence of an aborted reservation and cannot be submitted or retried.

There is no infinite journal recursion: preparation is a separate one-shot owner-authorized admission. If its first write was never persisted, a later observer cannot distinguish never-attempted from attempted-but-unpersisted admission. This implementation must explicitly decline reconstruction/retry of the same admission from absence. A future new owner action needs a new explicit request identity and current reviewed limits; it cannot silently resume the uncertain attempt. No current helper claims to implement that future admission producer.

Acceptance: missing/forged/wrong DB/wrong scope/stale preparation continuation fail before native reads; double invocation burns once; server91/connection-close/ACK-loss reservation cannot reuse the continuation; new client/read_commit/GET cannot reconstruct it; prepared and reserved journals both permanently reject replay; grant revision changes cannot replace a consumed slot. Retain all existing offline revoke/cancel and floor tests. All actual Mongo, namespace provisioning and independent review requirements remain.
