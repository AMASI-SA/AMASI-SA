# مركز ذكاء العملاء والمبيعات — عقد المرحلة الأولى

## حالة الوثيقة

- الاسم العربي: **مركز ذكاء العملاء والمبيعات**
- الاسم الإنجليزي: **Customer Intelligence & Sales Center**
- النسخة: `V1`
- الحالة: **نموذج تعاقدي وتجريبي فقط**
- أقصى مستوى استقلال مسموح: **تحليل واقتراح على بيانات تجريبية**
- القاعدة الافتراضية: **كل إجراء حي ممنوع ما لم تعتمد له مرحلة مستقلة لاحقًا**

هذه الوثيقة تثبّت حدود المرحلة الأولى التي تؤسس لخدمة العملاء بوصفها جهاز
الاستشعار والذاكرة لميزان، لا بوصفها بوت ردود منفصلًا. الهدف هو تجهيز بنية
تستوعب خلال السنوات القادمة فهم المحادثات، وتصنيف العملاء، واكتشاف اعتراضات
الشراء وفرص المنتجات، وربط النتائج بالمبيعات والمنتجات والحملات، مع بقاء
التنفيذ الحقيقي مغلقًا الآن.

## 1. الهدف

تعرض المرحلة الأولى واجهة متكاملة تمثّل مستقبل الخدمة، وتبرهن العقود وحالات
العمل وحواجز الأمان من خلال بيانات اصطناعية واضحة. يجب أن توضح الواجهة كيف
يستطيع ميزان مستقبلًا:

1. فهم النص والصوت والصورة في محادثة العميل.
2. تحديد نية العميل واعتراضه ودرجة استعداده للشراء.
3. اقتراح رد أو تصعيد لموظف.
4. بناء ملف عميل وتصنيفات قابلة للمراجعة.
5. اقتراح متابعة في الوقت الذي طلبه العميل.
6. إنشاء فرصة بيع أو فرصة منتج أو إشارة منافس.
7. تجهيز سلة محادثة ومسودة طلب دون إنشاء طلب حقيقي.
8. تحويل الأسئلة والاعتراضات إلى إشارات للمنتجات والحملات.
9. قياس اقتراحات الذكاء الاصطناعي وتعديلات الموظف والنتائج.
10. حفظ سجل قابل للتدقيق يبيّن المصدر والثقة والموافقة والنتيجة.

المرحلة الأولى لا تثبت أن هذه القدرات متصلة بمصدر حي، ولا تمنح أي صلاحية
تنفيذية.

## 2. نطاق المرحلة الأولى

### 2.1 المسموح

- صفحة Mezan OS V2 موحّدة ومتجاوبة.
- محادثات نصية وصوتية وصور **تجريبية**.
- نص تفريغ صوت ونتيجة تحليل صورة **تجريبيان**.
- ملخص المحادثة، النية، الاعتراض، درجة الثقة، ومصادر الاستنتاج.
- رد مقترح وزر تحويل للموظف في وضع المعاينة فقط.
- ملف عميل اصطناعي وتصنيفات واستنتاجات قابلة للمراجعة.
- مهام متابعة وفرص بيع ببيانات تجريبية.
- بطاقات فرصة منتج ومنافس محتمل.
- عرض معتمد تجريبي مع أثر ربحي تقديري ومصدر واضح.
- سلة محادثة ومسودة طلب ومعاينة رابط دفع وهمي غير قابل للاستخدام.
- مرشحات معرفة وحالات اعتماد تجريبية.
- مؤشرات جودة وأداء وسجل إجراءات تجريبي.
- تطبيع بيانات الواجهة، وحجب الحقول الحساسة، وإجبار جميع أعلام التنفيذ على
  `false`.
- اختبارات واجهة وعقود تثبت عدم وجود إجراء حي.

### 2.2 غير المسموح

- استقبال أو إرسال رسالة واتساب حقيقية.
- الاتصال بواجهات Meta أو WhatsApp أو Salla أو Qoyod أو شركات الشحن أو منصات
  الإعلانات.
- استخدام بيانات عميل حقيقية أو رقم هاتف أو بريد أو عنوان حقيقي داخل
  fixtures.
- إنشاء أو تعديل أو حذف منتج أو خيار أو سعر أو مخزون أو SKU.
- إنشاء خصم أو كوبون أو شحن مجاني أو تعويض.
- إنشاء طلب أو فاتورة أو سند أو شحنة أو رابط دفع.
- إنشاء أو تعديل أو إيقاف أو تشغيل حملة أو ميزانية أو إعلان أو إبداع أو جمهور.
- البحث الخارجي عن منافس أو جمع بياناته.
- تعديل موظف أو دور أو صلاحية أو إعداد مصادقة.
- تدريب نموذج أو تحديث معرفة منشورة تلقائيًا من محادثة واحدة.
- أي `POST` أو `PUT` أو `PATCH` أو `DELETE` تشغيلي باسم المركز.

## 3. نموذج ملكية البيانات

### 3.1 نواة ميزان

يمتلك ميزان ويضبط:

- هوية العميل الداخلية وخرائط الربط المسموح بها.
- الذاكرة المنظمة والتصنيفات والاستنتاجات.
- قواعد القرار والصلاحيات وحدود الاستقلال.
- المعرفة المعتمدة وسياسات الرد.
- فرص البيع والمنتجات والمتابعات.
- سجل الموافقات والتعديلات والنتائج.
- مقاييس الجودة والتحويل والربحية المنسوبة.

نموذج اللغة أو الرؤية مزود حسابي قابل للاستبدال، وليس مصدر الحقيقة ولا مالك
الذاكرة. يجب أن يمكن تغيير المزود أو إضافة نموذج محلي دون إعادة تصميم كيانات
ميزان.

### 3.2 مصادر الحقيقة المستقبلية

| الحقيقة | المصدر الرسمي | ما يسمح به مركز الذكاء |
|---|---|---|
| نص الرسالة ووقتها | مزود قناة التواصل | قراءة بعد ربط معتمد؛ لا تعديل للنص الأصلي |
| السعر والمخزون وخيارات المنتج | مصدر كتالوج المتجر المعتمد | قراءة لحظية فقط قبل أي اقتراح بيع |
| حالة الطلب والدفع والشحن | نظام الطلب/الدفع/الشحن الرسمي | قراءة الحالة؛ لا تخمين |
| الحملة والإعلان ومصدر الزيارة | منصة الإعلان/التحليلات | ربط بالإشارة عند توفر هوية موثقة |
| سياسة المتجر والأسئلة الشائعة | قاعدة معرفة ميزان المعتمدة | استخدام النسخة المنشورة فقط |
| نية العميل واعتراضه واحتمال الشراء | استنتاج ميزان | يحمل مصدرًا وثقة وتاريخًا وحالة مراجعة |
| نتيجة البيع والربح | الطلب المدفوع + محاسبة ميزان | قياس بعد المطابقة، لا من ادعاء النموذج |

### 3.3 عزل المستأجرين

أي كيان مستقبلي محفوظ يجب أن يحمل `user_id` أو `tenant_id` موثقًا من جلسة
المستخدم. يمنع قبول هوية المستأجر من جسم الطلب، ويجب أن تتضمن كل قراءة وكتابة
مستقبلية شرط المستأجر. تطابق رقم هاتف أو معرف خارجي بين متجرين لا يسمح بدمج
السجلات أو كشفها.

### 3.4 طبقات البيانات

```text
دليل أصلي → حقيقة مطبّعة → استنتاج/اقتراح → اعتماد → إجراء → نتيجة → سجل
```

- **الدليل الأصلي:** رسالة أو حدث من مصدر رسمي.
- **الحقيقة المطبّعة:** تمثيل موحد لا يغير معنى المصدر.
- **الاستنتاج:** تفسير يحمل ثقة وأدلة، وليس حقيقة مؤكدة.
- **الاقتراح:** رد أو متابعة أو فرصة أو تعديل مقترح.
- **الاعتماد:** قرار بشري أو قاعدة معتمدة ومحدودة.
- **الإجراء:** غير موجود في المرحلة الأولى.
- **النتيجة:** رد العميل أو طلب مدفوع أو فقد بيع بعد ربط مستقبلي.
- **السجل:** أثر غير قابل للإخفاء يربط القرار بمصدره واعتماده ونتيجته.

## 4. غلاف العقد المشترك

كل سجل معرفي أو استنتاجي مستقبلي يستخدم الحد الأدنى التالي:

```text
schema_version
tenant_id
entity_id
entity_type
source_type
source_refs[]
observed_at
created_at
updated_at
confidence
review_status
created_by
approved_by
expires_at
```

القواعد:

- `source_refs` مراجع داخلية محدودة، لا نسخ خام لبيانات حساسة.
- `confidence` رقم موحّد بين `0` و`1` ولا يستبدل الاعتماد.
- القيم المفقودة تبقى `null` أو `unknown`؛ لا تتحول إلى صفر أو حقيقة.
- أي استنتاج بلا دليل ظاهر يبقى `proposed`.
- المعلومة القديمة تحمل `expires_at` أو حالة `stale`.
- نماذج الاستجابة تمنع الحقول غير المعلنة.

## 5. الكيانات الأساسية

### 5.1 Conversation

يمثل جلسة تواصل واحدة:

```text
conversation_id
channel
external_conversation_ref
mezan_customer_id
status
started_at
last_message_at
assigned_to
consent_state
summary
```

الحالات المقترحة:

```text
open → needs_human / follow_up_due → resolved → closed
```

في المرحلة الأولى تكون `channel=demo` و`external_conversation_ref=null`.

### 5.2 Message

```text
message_id
conversation_id
direction
content_type
text
media_ref
transcript
sent_at
source_provenance
analysis_status
```

أنواع المحتوى المستقبلية: `text`, `image`, `audio`, `document`,
`interactive`. أي ملف تجريبي يجب أن يكون أصلًا اصطناعيًا محليًا، لا ملف عميل
حقيقيًا.

### 5.3 CustomerProfile

```text
mezan_customer_id
identity_refs[]
display_name_masked
preferred_language
contact_permission
segments[]
preferences[]
value_band
last_activity_at
```

الاهتمامات والميزانية والمقاس واللون المفضل استنتاجات مستقلة تحمل ثقة
ومصدرًا؛ لا تُكتب كحقائق ثابتة داخل الملف.

### 5.4 CustomerSignal

إشارة مستخرجة من دليل واحد أو أكثر:

```text
signal_id
signal_type
value
evidence_refs[]
confidence
review_status
valid_from
expires_at
```

أمثلة `signal_type`: نية شراء، اعتراض سعر، اعتراض شحن، انتظار راتب، مناسبة،
مقاس مفقود، لون مفقود، سلة متروكة، شكوى، أو عدم رغبة بالتواصل.

### 5.5 CustomerSegment

يمكن أن يحمل العميل أكثر من تصنيف في الوقت نفسه:

- جديد.
- مستفسر.
- جاهز للشراء.
- متردد بسبب السعر.
- متردد بسبب الشحن.
- ينتظر الراتب أو مناسبة.
- سلة متروكة.
- يحتاج مساعدة في الاختيار.
- متكرر.
- عالي القيمة.
- معرض للفقد.
- لديه شكوى تحتاج موظفًا.
- غير راغب بالتواصل.

التصنيف يفسر الإجراء المقترح، لكنه لا يمنح صلاحية تواصل أو خصم.

### 5.6 FollowUp

```text
follow_up_id
customer_id
conversation_id
reason
requested_time
timezone
product_refs[]
message_draft
allowed_offer_ref
attempt_limit
status
```

دورة الحياة المستقبلية:

```text
proposed → approved → scheduled → executed → responded
         → converted / closed / cancelled
```

في المرحلة الأولى لا يمكن تجاوز `proposed` أو `preview`; لا يوجد scheduler
ولا إرسال.

### 5.7 SalesOpportunity

```text

conversation_id
product_refs[]
```

القيمة والاحتمال تقديرات معلّمة، ولا تعد مبيعات حتى تطابق بطلب مدفوع.

يجب أن يشير الاقتراح إلى عرض معتمد سابقًا. لا يسمح للنموذج باختراع كود أو

كل عنصر يحتاج `product_id`, `variant_id`, `quantity`, وسعرًا ومخزونًا من

```text

```

دورة الحياة المستقبلية:

```text

      → approved_for_creation → created / blocked / cancelled
```

في المرحلة الأولى يتوقف عند `draft_preview`; الحالات التالية محجوزة وغير

### 5.14 KnowledgeCandidate

```text
knowledge_candidate_id
question_pattern
proposed_answer
evidence_refs[]
risk_class
review_status
version
```

دورة المعرفة:

```text
proposed → review → approved → published → retired
```

لا تنشر محادثة أو تعديل موظف مباشرة. الحقائق التشغيلية مثل السعر والمخزون لا
تخزن كإجابة ثابتة؛ تقرأ من المصدر وقت الاستخدام.

### 5.15 ActionProposal

هذا هو الغلاف المستقبلي لأي فعل يتجاوز التحليل:

```text

capability
target_ref
reason
inputs
expected_effect
risk_level
required_approvals[]
status
idempotency_key
```

دورة التنفيذ القياسية:

```text
proposal → preview → approval → execution → verification → audit → rollback
```

المرحلة الأولى تسمح بـ`proposal` و`preview` تجريبيين فقط. لا توجد أداة
`execution`.

### 5.16 AuditEvent

```text

event_type
entity_type
entity_id

after_summary
source_refs[]
approval_ref
```

لا يخزن السجل نص المحادثة الكامل أو Token أو بيانات دفع حساسة. يجب أن يثبت
ما اقترحه الذكاء، وما عدله الموظف، وما اعتمد، وما كانت النتيجة.

### 5.17 OutcomeAttribution

```text

customer_id
order_ref
campaign_ref
proposal_refs[]
outcome_type
revenue

```

لا تُنسب مبيعات للمساعد دون طلب مدفوع وهوية ربط قابلة للتدقيق. النتيجة
التجريبية تحمل `attribution_method=synthetic_demo`.

## 6. عقد واجهة المرحلة الأولى

أي payload تجريبي، سواء أتى من fixture محلي أو endpoint قراءة، يجب أن يحتوي:

```json
{
  "schema_version": "customer-intelligence-v1",
  "mode": "demo_read_only",
  "source_provenance": "synthetic_fixture",
  "generated_at": "ISO-8601",
  "safety": {
    "live_channels_enabled": false,
    "external_network_allowed": false,
    "database_writes_allowed": false,
    "message_send_allowed": false,
    "product_mutations_allowed": false,
    "discount_mutations_allowed": false,
    "order_creation_allowed": false,
    "payment_link_creation_allowed": false,
    "advertising_mutations_allowed": false
  }
}
```

قواعد الواجهة:

- تطبيع أي payload غير موثوق وإجبار أعلام التنفيذ على `false`.
- إظهار شارة ثابتة: **بيانات تجريبية — لا إرسال أو إجراء حقيقي**.
- تسمية الصور والصوت والتحليل والروابط الوهمية بوضوح.
- عدم إنشاء `href` صالح لمعاينة رابط الدفع.
- تعطيل أزرار التنفيذ مع سبب ظاهر، لا إخفاؤها فقط.
- عدم عرض رقم هاتف أو بريد أو عنوان أو هوية دفع كاملة.
- كل عنصر تفاعلي يحمل `data-testid` واسمًا وصوليًا مناسبًا.

إذا أضيف backend للمرحلة الأولى، يكون authenticated وtenant-scoped وGET-only.
أي POST تجريبي يجب أن يبقى داخل حالة واجهة محلية، لا داخل API تشغيلي.

## 7. الربط المستقبلي مع المنتجات

مركز ذكاء العملاء لا يعدل المنتج مباشرة. التكامل المستقبلي يكون بعقد اقتراح:

```text
CustomerSignal
    → ProductOpportunity
    → مراجعة
    → Product Change Proposal
    → مركز المنتجات
    → معاينة الفرق
    → اعتماد مستقل
    → تنفيذ وتحقق وسجل
```

قد يحمل الاقتراح:

- الأسئلة المتكررة عن الوصف.
- المقاسات والألوان المطلوبة وغير المتوفرة.
- صورًا خارجية متكررة بعد إخفاء الهوية.
- سبب ارتباك العميل في صفحة المنتج.
- طلب منتج غير موجود.
- المنتجات الحالية الأقرب.
- عدد العملاء المختلفين ودرجة الطلب والثقة.

مركز المنتجات هو صاحب صلاحية تعديل الوصف والصور والخيارات والمخزون. اعتماد
فرصة منتج داخل مركز العملاء لا يساوي اعتماد تغيير المنتج.

## 8. الربط المستقبلي مع الحملات

مركز ذكاء العملاء يرسل أدلة وتحليلات، لا أوامر حملات:

```text
Conversation + Campaign Identity
    → Objection / Qualified Lead / Outcome
    → Campaign Feedback Signal
    → مدير الإعلانات
    → اقتراح تعديل
    → معاينة واعتماد
    → تنفيذ محدود وتحقق
```

الإشارات المفيدة مستقبلًا:

- جودة العملاء القادمين من كل حملة أو إعلان.
- الاعتراضات المرتبطة بوعد أو صورة أو صفحة هبوط.
- التحول من محادثة إلى طلب مدفوع.
- المنتجات أو الألوان أو المقاسات المطلوبة من جمهور حملة.
- الربح بعد الخصم والإعلان عند توفر مصادره الرسمية.
- الشكاوى أو الإلغاءات المنسوبة بهوية موثقة.

يمنع استخدام مجرد ذكر العميل لإعلان كأساس إسناد مؤكد. يجب أن يحمل الربط
`campaign_id`, `ad_id`, `creative_id`, و`attribution_method` عند توفرها.
لا يفعّل أي إشارة تعديل ميزانية أو إيقاف حملة تلقائيًا في المرحلة الأولى.

## 9. الربط المستقبلي مع الطلب والدفع

المسار المعتمد مستقبلًا:

```text
سلة محادثة
→ تحقق السعر والمخزون والمتغير
→ مراجعة موظف
→ ملخص واضح للعميل
→ موافقة صريحة من العميل
→ Order Engine
→ إنشاء الطلب
→ Payment Provider
→ رابط رسمي
→ إرسال عبر قناة معتمدة
→ تحقق من الدفع
→ سجل النتيجة
```

أي معلومة غير مؤكدة توقف المسار. لا ينشئ المركز رقم طلب أو رابط دفع، بل يطلب
ذلك مستقبلًا من محرك الطلبات عبر قدرة مستقلة ومحدودة.

## 10. مستويات الاستقلال

| المستوى | الوصف | مثال | حالة V1 |
|---|---|---|---|
| `L0` | قراءة وتحليل | تلخيص المحادثة واستخراج اعتراض | تجريبي فقط |
| `L1` | اقتراح | رد، متابعة، عرض معتمد، فرصة منتج | تجريبي فقط |
| `L2` | تنفيذ بعد اعتماد موظف | إرسال رد أو إنشاء مسودة رسمية | ممنوع |
| `L3` | تنفيذ تلقائي لحالات آمنة | إجابة حالة طلب موثقة | ممنوع |
| `L4` | إدارة ضمن حدود | عروض وطلبات وحملات ضمن سقوف | ممنوع |
| `L5` | تشغيل واسع برقابة واستثناءات | إدارة شبه ذاتية متعددة الأقسام | ممنوع |

يرتفع المستوى لكل capability بصورة مستقلة؛ لا يوجد مفتاح يمنح النظام مستوى
واحدًا لكل شيء. القدرة الافتراضية `deny`, ويشترط للرفع:

- مصدر بيانات موثوق.
- قياس دقة وعتبة نجاح.
- صلاحية واضحة.
- سقف مالي أو تشغيلي.
- مراجعة أخطار وفشل.
- زر إيقاف.
- تحقق بعد التنفيذ.
- سجل وتراجع.

يرجع النظام تلقائيًا إلى `L1` أو `L0` عند نقص البيانات أو ارتفاع الخطأ أو
انتهاء الصلاحية.

## 11. الخصوصية والاحتفاظ

### 11.1 مبادئ

- تقليل البيانات إلى ما يلزم للغرض.
- فصل الهوية ووسيلة الاتصال عن الاستنتاجات قدر الإمكان.
- حجب البيانات في الواجهة والسجلات والـprompts.
- عدم إرسال أسرار أو Tokens أو بيانات دفع أو عنوان كامل إلى نموذج.
- تشفير البيانات أثناء النقل والتخزين عند دخول المرحلة الحية.
- تسجيل الوصول والتصدير والحذف.
- احترام رفض التواصل فورًا.
- عدم استخدام بيانات المحادثات لتدريب مزود خارجي.
- اختيار إعدادات مزود تمنع التخزين أو تقلله عندما تكون متاحة.
- دعم الحذف أو إخفاء الهوية مع استثناء أي التزام احتفاظ معتمد.

### 11.2 المرحلة الأولى

لا تحتوي المرحلة الأولى بيانات شخصية حقيقية. تستخدم fixtures اصطناعية فقط،
وتمنع نسخ محادثة أو ملف عميل حقيقي إلى الكود أو الاختبارات أو لقطات العرض.

### 11.3 سياسة احتفاظ مقترحة للمرحلة الحية

الأرقام التالية defaults تقنية مقترحة وليست اعتمادًا قانونيًا. يجب مراجعتها
واعتمادها قبل أي ربط حي:

| نوع البيانات | الحد المقترح | الإجراء بعده |
|---|---:|---|
| ملف صوت أو صورة خام | 30 يومًا كحد أقصى | حذف الملف والإبقاء على نتيجة مخففة عند الحاجة |
| نص محادثة خدمة العملاء | 180 يومًا | حذف أو إخفاء الهوية وفق الغرض والموافقة |
| استنتاج غير معتمد | 90 يومًا | انتهاء وحذف |
| تفضيل أو تصنيف معتمد | 365 يومًا دون دليل جديد | تحويل إلى stale ثم إعادة التحقق أو الحذف |
| متابعة مغلقة | 90 يومًا بعد الإغلاق | إخفاء الهوية أو الحذف |
| فرصة منتج مجمعة ومجهلة | ما دامت فعالة | مراجعة سنوية وحذف الأدلة الفردية |
| معرفة معتمدة | حتى الاستبدال أو التقاعد | حفظ الإصدارات دون بيانات عميل |
| سجل قرار غير مالي | 24 شهرًا | أرشفة أو حذف وفق السياسة المعتمدة |
| سجل طلب أو دفع مستقبلي | سياسة النظام الرسمي | لا يحددها مركز العملاء |

يجب أن تكون مدد الاحتفاظ قابلة للضبط حسب البيئة ونوع البيانات، وألا يستطيع
النموذج تمديدها.

## 12. حواجز `no-live-actions`

الحواجز دفاع متعدد الطبقات:

1. **واجهة:** شارة demo ثابتة، أزرار تنفيذ disabled، وروابط وهمية غير قابلة
   للنقر.
2. **خدمة frontend:** fixture محلي أو GET فقط، ولا دوال `send`, `create`,
   `update`, `delete`, `publish`, أو `execute`.
3. **API:** إن وجد، GET-only وresponse models مغلقة.
4. **الشبكة:** لا عميل HTTP لمزود واتساب أو سلة أو الإعلانات داخل حزمة V1.
5. **قاعدة البيانات:** لا insert/update/delete/replace/bulk-write بسبب فتح
   الصفحة أو التفاعل معها.
6. **الأدوات:** لا أداة تنفيذ متاحة للنموذج.
7. **الصلاحيات:** backend هو الحد النهائي؛ إخفاء زر في الواجهة ليس صلاحية.
8. **الاختبارات:** sentinels تثبت عدم تسرب سر أو PII أو زر حي.
9. **CI:** حارس مسارات وحارس مصدر يرفضان موصلات الشبكة وأفعال الكتابة.
10. **Kill switch مستقبلي:** يبدأ `false` ولا يفعّل من واجهة المستخدم.

أي payload يدعي أن فعلًا حيًا متاح يجب أن يصححه frontend إلى `false`، ويجب أن
يرفضه backend أيضًا.

## 13. حالات الفشل الآمن

- إذا كانت الثقة منخفضة: يعرض عدم اليقين ويقترح موظفًا.
- إذا غاب السعر أو المخزون: يمنع سلة الطلب.
- إذا تعارضت مصادر الحقيقة: يمنع الاقتراح التنفيذي ويعرض التعارض.
- إذا انتهت صلاحية الاتصال: تتوقف القدرة المعتمدة عليه.
- إذا طلب العميل إيقاف التواصل: تلغى كل متابعة.
- إذا لم تتطابق هوية العميل: لا تدمج الملفات.
- إذا كانت صورة أو رسالة غير واضحة: لا يدعي مطابقة مؤكدة.
- إذا غاب معرف الحملة: تبقى الإشارة `unattributed`.
- إذا أخفق النموذج أو تجاوز المهلة: تعاد نتيجة مسيطر عليها بلا إرسال.
- إذا ارتفعت الأخطاء: تنخفض القدرة تلقائيًا إلى اقتراح أو تحليل فقط.

## 14. متطلبات الواجهة

- RTL إلزامي، عناوين Tajawal ونصوص Cairo.
- أرقام إنجليزية مع تنسيق `en-US`.
- سطح فاتح وبطاقات بيضاء مسطحة بحدود خفيفة و`rounded-xl`.
- لا glassmorphism ولا ظلال ثقيلة.
- ألوان الحالة لا تستخدم وحدها؛ تضاف أيقونة ونص.
- كل عنصر تفاعلي يحمل `data-testid`.
- التبويبات الكثيرة قابلة للتمرير أفقيًا على الشاشات الصغيرة.
- عرض المصدر والثقة والحالة والإجراء التالي في بطاقة كل اقتراح.
- بيانات العميل في أمثلة الواجهة masked أو اصطناعية.
- معاينة رابط الدفع موسومة **وهمي** ولا تحمل URL تشغيليًا.

## 15. اختبارات القبول

يجب أن تثبت الاختبارات المستهدفة:

### Frontend

- ظهور اسم المركز وشارة demo.
- وجود الوحدات الرئيسية وحالاتها المنظمة.
- ترتيب حالات المتابعة وفرص المنتجات والاستقلال.
- تطبيع payload وإجبار جميع أعلام التنفيذ على `false`.
- عدم ظهور أزرار إرسال أو إنشاء طلب أو دفع أو حملة قابلة للتنفيذ.
- عدم ظهور sentinel يمثل Token أو PII أو رابط دفع حقيقيًا.
- وجود `data-testid` على التبويبات والأزرار.
- بقاء العرض قابلًا للقراءة على الجوال دون شبكة ثابتة عريضة.

### Backend

- مصادقة وعزل مستأجر.
- GET-only.
- صفر كتابة لقاعدة البيانات.
- صفر اتصال بمزود خارجي.
- response schema مغلق.
- القيم المجهولة تبقى `null` أو `unknown`.
- عدم تسرب أسرار أو بيانات شخصية.
- عدم استيراد مسار تشغيلي للطلبات أو المنتجات أو الخصومات أو الحملات.

### Regression

- بناء frontend ينجح.
- اختبارات مركز الذكاء المستهدفة تنجح.
- اختبارات AI analysis وApps & Integrations ذات الصلة تنجح.
- لا تعديل لملفات رفع المنتجات أو التجهيز أو الموظفين أو الأدوار أو
  الصلاحيات.

## 16. بوابة الانتقال إلى المرحلة الثانية

لا يبدأ الربط الحي حتى تعتمد بصورة مستقلة:

1. قناة واتساب ومزودها وصلاحياتها وشروط استخدامها.
2. سياسة خصوصية واحتفاظ وحذف وموافقة تواصل.
3. مخطط هوية العميل ومنع الدمج الخاطئ.
4. قراءة موثوقة للمنتجات والأسعار والمخزون والطلبات والشحن.
5. مجموعة تقييم واقعية مجهلة لقياس الدقة والهلوسة.
6. لوحة جودة وقواعد تصعيد وفشل آمن.
7. صلاحيات موظفي خدمة العملاء.
8. حدود المعدل والتكلفة اليومية والشهرية.
9. kill switch واختبار توقفه.
10. قرار مكتوب يحدد القدرات التي تنتقل من `L1` إلى `L2`.

حتى تحقق هذه البوابة، تبقى V1 نواة تعاقدية وتجريبية: تفهم كيف سيعمل ميزان
وتعرض قراراته المستقبلية، لكنها لا تتصرف باسم المتجر أو العميل.
